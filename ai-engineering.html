Part I · The new layer

What changed, and what did not

A language model is a new kind of component, one whose output no unit test can pin down, but most of what makes an AI service work in production is engineering you already know, applied to that component with care.

At a glance
  • The genuinely new part: the same input gives different outputs, any text that reaches the prompt can try to instruct the model, and every call has a price in tokens.
  • The familiar part: seams and adapters, timeouts, streaming, access control, observability, capacity, supply chain. All of it still applies, and most of an AI service is this.
  • Tests prove the code; evals measure the model and prompt together, as a pass rate over repeated runs.
  • A safety property that matters goes in code, not in the prompt: a prompt rule is a probability.
  • In the reference service, the AI-specific logic is two small modules; everything around them is the standard platform.

The AI part is small

The reference service is an incident triage assistant: an on-call engineer asks about the alerts their teams can see, and a model answers from those alerts and the teams' runbooks, streaming its answer and citing the runbook sections it used. Its AI-specific logic lives in two modules, one deciding what the model sees and one talking to any OpenAI-compatible endpoint. Everything else (sign-in, roles, database isolation, rate limits, streaming, telemetry, deployment) is the same platform a service without a model would need, and that is deliberate: a new project replaces the domain and the prompt, and keeps the rest.

What is genuinely new

Tests and evals are different tools

A unit test proves the code does what it says. It cannot tell you whether answers stay grounded in the alerts, whether the model obeys instructions smuggled into alert text, or whether an answer mentions another team's incident. Those depend on the model and the prompt together, and the same case can pass twenty-nine runs and fail the thirtieth.

Safety in code, not in the prompt

A rule in a prompt is a probability. In the reference service, "never repeat credentials" still failed about one run in a hundred, and telling two wordings of that rule apart at such a rate takes thousands of runs. Redacting credentials in code before any model call cannot fail for the formats it recognizes, and keeps them from the provider too; the prompt rule stays as a second layer for formats the code does not know. The same principle bounds prompt injection: the prompt reduces the rate and evals measure it, but what limits the damage is architectural. The model has no tools that change anything, it is given only what the asker may read, and its output is rendered as text (Chapter 9).

Questions

  1. Name three things about a language model that are genuinely new to an experienced engineer, and three that are existing skills applied.

    Answer

    New: non-deterministic output measured as pass rates; untrusted text that can instruct the model; tokens as the unit of cost and latency (also: retrieval quality, judge calibration, reasoning tokens). Applied: a seam over the provider, timeouts and cancellation, streaming, access control over the context, observability, supply-chain and contract review.

  2. What can an eval tell you that a unit test cannot?

    Answer

    How often the model and prompt together behave as intended, such as staying grounded, refusing what the context does not support, resisting injected instructions and never crossing teams, as a pass rate over repeated runs with a real model.

  3. Why is a prompt rule not enough for a safety property?

    Answer

    It is followed with some probability, not always, and rare failures need thousands of runs to measure. Code (redaction, access-controlled context, no state-changing tools) enforces the property every time for the cases it covers.

Part II · How models run

How a model produces text

A language model turns text into tokens, scores every possible next token, samples one, appends it and runs again; latency, cost, memory and the variability that evals must measure all follow from that loop.

At a glance
  • One forward pass per output token. Prices, limits and speed are all counted in tokens.
  • Two phases: prefill reads the prompt in parallel and sets the time to first token; decode writes one token at a time and sets tokens per second.
  • Sampling (temperature, top-p) is why the same prompt answers differently, and why evals repeat runs.
  • The context window holds input and output together; hidden reasoning spends the output budget too.
  • The KV cache holds every earlier token's keys and values in GPU memory, and caps how many requests fit at once.
Then and now
ThenNowWhy it changed
Recurrent networks reading one word at a timeTransformers attending to the whole context at onceAttention trains in parallel and scales with data and compute.
Context of a few thousand tokensWindows of hundreds of thousandsLong contexts are now practical, but cost memory and time, and the middle is used worst.
A model answers directlyReasoning models think in hidden tokens firstSpending tokens on intermediate steps improves hard answers, at a price in tokens and latency.

The loop

Attention, at a lead's level

Each layer does two things to every token's vector: attention mixes in information from other tokens, then a feed-forward network transforms each vector on its own. For attention, each token's vector is projected into a query (what it is looking for), a key (what it contains) and a value (what it passes on). A token's output is the average of the values, weighted by how well its query matches each key. Several heads do this in parallel, each learning a different kind of relation.

Logits, sampling and temperature

Prefill and decode: two phases, two bottlenecks

The KV cache

Every layer keeps the keys and values of all tokens so far in GPU memory, so decode computes them only for the new token. Per sequence it takes roughly two (keys and values) × layers × KV heads × head size × bytes per value × tokens: gigabytes for long contexts. It limits how many requests fit on a GPU at once; in the reference measurements, eight parallel slots of a 20-billion-parameter model used 38 GB, most of it cache. Paged allocation, grouped-query attention (fewer KV heads, a property of the model) and a quantized cache shrink it, and prefix caching reuses the cache of a shared prompt prefix across requests, which is the self-hosted form of a provider's prompt caching (Chapter 10).

The context window, and reasoning tokens

  • The model client reports an empty answer as its own error, llm_empty_answer, with a metric and an alert on truncated answers.

A bigger context window is not free: prefill time and cache memory grow with it, and models use the middle of a long context worst. Send only what the question needs, ordered so that the most important material is at the start or the end.

Questions

  1. Which phase sets the time to first token, which sets tokens per second, and what makes each worse?

    Answer

    Prefill sets the time to first token and grows with the prompt's length; it is compute-bound. Decode sets tokens per second; it is memory-bandwidth-bound and slows as more streams share the GPU or the cache grows.

  2. What does temperature do, and why do evals repeat runs?

    Answer

    It divides the logits before softmax: lower sharpens toward the likeliest token, higher flattens. Sampling from the distribution means the same prompt gives different answers, so a case's behavior is a rate, measured over many runs.

  3. What is the KV cache, and why does it limit concurrency?

    Answer

    The stored keys and values of every earlier token, per layer, so decode does not recompute them. It lives in GPU memory and grows with each sequence's length, so it caps how many sequences fit on a GPU at once.

  4. Why can a reasoning model return an empty answer?

    Answer

    Its hidden reasoning is output and counts against the output limit; with a small limit or high effort, it can spend the whole budget thinking before writing anything visible.

Part II · How models run

Serving models

Serving a model is a trade between throughput, which is the cost, and per-stream speed, which is the user's experience; and an application stays free to change the model or the provider only if it reaches every model through one small seam.

At a glance
  • Batching runs several sequences per forward pass: total throughput rises a lot, and each stream slows a little.
  • GPU memory holds the weights (parameters × bytes each) plus the KV cache, which grows with concurrency and context.
  • Quantization saves memory and speeds decode, and costs quality unevenly: evaluate the quantized model itself.
  • Replicas when the model fits on one GPU; tensor parallelism within a node when it does not; pipeline parallelism across nodes only when you must.
  • One OpenAI-compatible seam, a mock behind it for tests, and a gateway when several services share models and quotas.
Then and now

Throughput and latency: batching

GPU memory, precision and loading

Loading copies the weights from disk to the GPU, which takes tens of seconds for a large model, so a cold start is a latency spike. Keep models resident and warm them before traffic: Ollama, for example, unloads a model after five idle minutes by default, so the first call after a pause pays the load. A model that does not fit spills to the CPU, very slowly, or must be split across GPUs. One failure is worth knowing about: in the reference build, a GPU container silently lost access to its GPU after a day of use and loaded models on the CPU instead, with no error anywhere. The only sign was that judge calls taking about a minute had not finished after ten; checking which processor a model is loaded on, and recreating the container, fixed it.

Parallelism across GPUs

The serving architecture, and the seam

In the repoapps/api/app/llm.pyprovider failures, mapped to the service's own

The seam's error mapping. Routes and the prompt module see only these few typed errors, whichever provider answers.

  • Each error has a stable code that metrics, alerts and the browser key on: a timeout, rate limiting, unavailability, a rejected request.
  • A 400-class rejection is the service's own mistake (key, model name, parameters); retrying will not help, so it is not retried.
  • Failures can arrive mid-stream, after the response has started, which is why the stream carries its own error event (Handbook 2, Chapter 10).
def _provider_errors(what: str) -> Iterator[None]:
    """The SDK maps transport failures to its own exceptions, both before
    and during a stream; these become ours. Order matters: APITimeoutError
    is a subclass of APIConnectionError."""
    try:
        yield
    except openai.APITimeoutError as exc:
        raise LLMTimeout(f"{what} took too long to respond") from exc
    except openai.RateLimitError as exc:
        raise LLMRateLimited("the model provider is rate limiting us") from exc
    except (openai.APIConnectionError, openai.InternalServerError) as exc:
        raise LLMUnavailable("the model provider is unavailable") from exc
    except openai.APIStatusError as exc:
        # 400/401/403/404: our request or configuration is wrong (key,
        # model name, parameters) - retrying will not help.
        raise LLMError(f"the model provider rejected the request ({exc.status_code})") from exc
    except openai.APIError as exc:  # e.g. an error event inside the stream
        raise LLMUnavailable("the model provider failed mid-answer") from exc

Managed API or self-hosted?

How to say it

"Batching trades per-stream speed for throughput; we set concurrency against a latency target, and the KV cache caps it."

"Every model call goes through one OpenAI-compatible seam with typed errors and explicit timeouts, so a new provider or a gateway is a configuration change, plus an eval run."

Questions

  1. Why does batching raise throughput but slow each stream?

    Answer

    Decode is memory-bound: each forward pass reads all the weights. Batching reads them once for several sequences, so total tokens per second rises; each sequence now shares the pass with others, so its own rate drops.

  2. How much memory do a 20-billion-parameter model's weights take at 16 and at 4 bits, and what uses the rest?

    Answer

    About 40 GB and about 10 GB. The rest holds the KV cache for concurrent sequences, plus activations and runtime overhead.

  3. When is self-hosting cheaper than a managed API?

    Answer

    Only when the GPU is kept busy: an idle GPU is still paid for. For the reference service, break-even against a small managed model was about two million questions a month. Data residency or sustained high load can justify it for other reasons.

  4. What does a gateway add once several services call models?

    Answer

    Shared authentication and keys, request and token limits per tenant, routing to the cheapest suitable model, fallback on errors or rate limits, and central logging and cost tracking.

Part III · Building with models

Retrieval-augmented generation

Retrieval-augmented generation is a pipeline of a dozen stages that each fail differently: debug it backwards from the answer, measure retrieval apart from generation, and enforce who may see what inside the retrieval query itself.

At a glance
  • "Use a vector database" names one stage out of twelve. Most failures are in chunking, filtering, fusion and context, not the index.
  • The chunk is both the unit you find and the unit the model reads; split at document structure by default.
  • Hybrid search: keywords find exact identifiers, embeddings find paraphrases, rank fusion merges them without calibrating scores.
  • A tenant filter applied after an approximate index can return nothing, silently. Filter in a form the planner can use first.
  • Measure retrieval with recall@k and MRR on labeled questions; a chunk never retrieved cannot be used, whatever the prompt says.

The pipeline, and how to debug it

Chunking

Embeddings, similarity and indexes

An embedding model maps a text to a vector so that similar meanings point in similar directions. Query and document are embedded separately, so documents are embedded once, ahead of time. Three facts cause most embedding bugs. Asymmetric models want task prefixes (search_query: , search_document: ), which are part of the model. Vectors from different models, dimensions or prefixes are incomparable, and nothing errors: similarity search keeps returning rows, now meaningless, so the reference service stores an embedding key with every vector and searches only today's. And a vector is as sensitive as its text: research has recovered much of the original text from embeddings.

On vectors normalized to length one, cosine, dot product and Euclidean distance rank identically; cosine is the safe default when normalization is not guaranteed. Exact search compares every row and is fine up to many thousands. Approximate indexes trade recall for speed by design: HNSW is a layered graph, fast and memory-hungry, with build-time parameters (m, ef_construction) and a query-time candidate width (ef_search, 40 by default in pgvector); IVFFlat clusters the vectors and needs data to train on. In Postgres, HNSW comes from the pgvector extension, the operator class must match the query's operator, and the query must be shaped ORDER BY embedding <=> $q LIMIT n, or Postgres quietly scans every row.

Measuring retrieval

Context, citations and freshness

  • Too few chunks, and the model invents. Given one of the four sections it needed, it wrote a step the runbook never had, without its safety conditions, and cited it with full authority. The reference service now puts four sections in context.
  • Too many, and cost, latency and dilution grow; models use the start and end of a long context best, so the best chunks go first, deduplicated.
  • Citations are numbered and verified. A number outside the list is an invented citation, counted as a hallucination signal. Parse tolerantly: asked for [R1], the model also wrote (R1), 【R1】 and a bare R1. A valid citation proves a chunk was referenced, not that it supports the claim; that needs a judge.
  • Freshness and deletion. Show each chunk's date; ingest idempotently by document identity and content hash, re-embedding only what changed; and make deletion reach the chunks, or deleted text keeps being retrieved.
  • No distance cutoff by default. With one model, relevant sections reached distance 0.43 while unanswerable questions began at 0.41. A cutoff is per model, and only after measuring; otherwise the prompt and evals handle irrelevant chunks.

Documents are untrusted input too: an instruction planted in a document is indirect prompt injection, and anyone who can edit a document can attempt it. The same architectural bounds apply as for any injected text, and secrets in documents reach the embedding provider on every save, so redaction must come before any model call, not only before the chat prompt (Chapter 9).

Questions

  1. An answer is wrong. In what order do you examine the pipeline, and why?

    Answer

    Backwards from the answer: the check, generation, the prompt, the context, fusion, each retriever, chunking, parsing, ingestion. Stop at the first stage that is wrong; everything after it only looks wrong.

  2. Why combine keyword and semantic search, and how are their results merged?

    Answer

    Keywords find exact rare tokens such as error codes; embeddings find paraphrases. Reciprocal rank fusion merges them by rank alone, so their scores need no calibration; a reranker fixes its equal weighting.

  3. What is the overfiltering trap, and how is it avoided?

    Answer

    An approximate index returns its nearest candidates and the tenant filter runs after; for a small tenant all candidates may belong to others, so nothing is returned. Use a filter the planner can apply first, iterative scans, or per-tenant indexes or partitions.

  4. What do recall@k and MRR measure, and what can a 19-question benchmark not tell you?

    Answer

    Recall@k: whether a relevant chunk is in the top k. MRR: how high the first relevant chunk ranks on average. A small benchmark shows each model works; it cannot rank models whose difference is a couple of questions.

Tools, and the confused deputy

MCP: the Model Context Protocol

MCP's security model rests on the server, not on hints. Tool annotations such as "read-only" are hints and must not be trusted; servers validate, authorize and rate-limit; tokens are never passed through to downstream services; and hosts confirm sensitive calls. Tool poisoning is a malicious server whose tool descriptions, or instructions returned on connect, reach the model as prompt text: install MCP servers the way you install dependencies. A large public server illustrates the trade-offs: a handful of tools, one of which runs model-written code in a sandbox that can reach any API of the platform. The short tool list keeps the prompt cheap and the choice easy, but the power then sits in one tool, so the credentials behind it, not its "destructive" hint, set the blast radius. Its results include a record of what actually ran, and its description tells the model to check that record before trusting the return value.

Skills are a related idea: a folder of markdown whose short description sits in the model's context and whose full text loads only when a task matches. A skill teaches how to do a job; a tool does it. Both are instruction channels from a source you must trust.

def fisher_worse(fails_now: int, runs_now: int, fails_before: int, runs_before: int) -> float:
    """One-sided Fisher exact test: the chance of at least `fails_now`
    failures among the current runs if both sets of runs shared one failure
    rate. Small = the current runs are really worse."""
    total_runs, total_fails = runs_now + runs_before, fails_now + fails_before
    denominator = math.comb(total_runs, runs_now)
    return (
        sum(
            math.comb(total_fails, x) * math.comb(total_runs - total_fails, runs_now - x)
            for x in range(fails_now, min(total_fails, runs_now) + 1)
        )
        / denominator
    )

Read the answers before trusting a number

The first runs of the reference harness found four wrong checks and one model failure: a correct answer written with a non-breaking hyphen failed a substring check (so every text check now normalizes typography and case first); a phrase list missed "I'm not seeing any alerts"; and a judge rubric asked for the wrong thing, twice. Worse than a missing check is one that passes wrong answers: the off-topic case once checked only that the answer did not say "Paris", and a later prompt answered "There are no alerts." with an alert in the list, in 8 runs of 40, all of them green.

How many runs: the statistics that matter

  • The rule of three. Zero failures in n runs means the failure rate is below about 3/n, with 95% confidence. "Never" is not a claim: 0 leaks in 200 runs means "below 1.5%".
  • Small samples hide rare failures. In the reference project, 110 passing calls missed a behavior that later showed up 8 times in 40 runs, and a prompt leak that happened 5 times in 200.
  • The target is the bound, not the number of runs. One leak in 200 runs puts the bound at 2.35%, over a 1.5% target; 400 more runs with one more leak brought it to 1.05%. Each failure seen raises the runs needed.
  • Is a difference real? Fisher's exact test: 5 leaks in 200 against 0 in 200 would happen with probability 0.03 if both prompts leaked equally, so the difference is real; 1 against 0 means nothing. In the gate, 0 to 1 failures in 10 runs is noise (p = 0.5), and 0 to 5 is a regression (p = 0.016).

The judge

A judge is a second model asked a yes-or-no question about an answer: whether an answer that quotes a malicious command warns against it or recommends it, or whether "I don't have that information" declines correctly. It is a model, so it can be wrong. The reference rules: calibrate it against answers a person labeled YES and NO, including hard ones (a correct answer in odd words, a bad answer that looks fine), with at least one NO per criterion, or a judge that always says YES looks perfect; use a model from another family than the one under test, at temperature 0; ask for a short reason, then the verdict; and fail the run when a verdict is missing.

Part V · Making it safe

AI security

Anything a model reads can try to instruct it, and no prompt reliably stops that; so the controls that hold sit outside the model: what it may read, what it may do and with whose rights, who confirms, and who can find out afterwards.

At a glance
  • Follow the chain (what the model reads, the model, its decision, a tool, a system) and at every arrow ask: what if the model is wrong, or its context was written by someone else?
  • Indirect injection is the dangerous kind: the instruction arrives inside content read for the user, and the attacker never touches the system.
  • The damage is set by what the model can do, not what it is told. No tools, or read-only tools acting as the asker, bound it.
  • Never combine untrusted input, private data and a way to act or send data out without a person in between.
  • Redact secrets in code before every model call; render output as text; keep an append-only audit trail of what the model was given.

The chain, and a control at every arrow

Prompt injection is bounded by architecture

Direct injection is the user typing the instruction. Indirect injection arrives inside content the model reads for the user: an alert, a document, a web page, an email, a tool's output. Indirect is the dangerous one, because the victim is the person asking and the attacker never touches the system. Prompt-level and model-level defenses (delimiters, marking untrusted text, classifiers, fine-tuning) lower the rate against known attacks, and published research found adaptive attacks broke all twelve defenses it tested, most of them more than 90% of the time. In security, a 95% block rate is a failing grade. The prompt reduces the rate and evals measure it; the architecture limits the damage.

Secrets: redaction, measured

  • Redact before every model call: the prompt and the text sent for embedding. It is deterministic for what it recognizes, and keeps secrets from the provider too. The prompt's own rule ("never repeat credentials") failed about one run in a hundred; with redaction, a planted password came back 0 times in 200.
  • Leave non-secrets alone: masks, $VARIABLE references, placeholders, and words like max_tokens, which is why names must end with the keyword.
  • A regular expression run on text others write is an attack surface. Scans that restarted at every match were quadratic: 100,000 characters of one repeated word took 6.4 seconds on the event loop. Every scan is now bounded, and a test keeps hostile input linear.
  • Redaction removes formats, not facts. "Payroll failed for 1,200 employees" survives it. What it can never catch is a secret with no known name, format or position; the fix for those is at the source.

Cost and performance

A model's bill is requests × tokens per request × price per token; knowing which factor moved explains every cost jump, and each lever that lowers it has a quality cost that only evals can measure.

At a glance

The levers

Distributed AI systems

Model calls are slow, flaky, paid and bursty, so any work the user's immediate answer does not need goes behind a queue, with leases, idempotent effects, jittered retries, a dead-letter queue and a circuit breaker; the patterns are classic, and the bill makes them matter more.

At a glance
  • Ingestion, embedding, re-indexing, batch evaluation and long agent jobs go behind a queue: the request returns a job id, workers go at their own pace.
  • At-least-once delivery plus an idempotent effect is effectively once; a retried model call is still paid twice.
  • Retry only what can succeed, at one layer, with capped exponential backoff and full jitter.
  • A circuit breaker stops calling a failing provider; bulkheads keep one workload from starving another.
  • Guard every asynchronous write with a version check, or an older job can overwrite newer results.

Retries, breakers and bulkheads

The reference service applies the lighter versions of these patterns on its interactive path: its model client retries once, before the first token only; a slow question embedding degrades to keyword search rather than retrying; its rate limiter fails open; and when most searches fall back, an alert fires. Backpressure is the other half: when producers outrun workers, something must give, whether a bounded queue that refuses with a 503 and Retry-After, producers that slow down, or low-priority work dropped. A model server is a queue too: with one slot, throughput stayed flat under load, and only the wait grew.

Races, locks and consistency

  • Optimistic locking for rare conflicts, such as two editors of one runbook: write WHERE version = :read, and answer 409 on zero rows.
  • Pessimistic locking (SELECT ... FOR UPDATE) for frequent conflicts or expensive retries; it holds a connection and invites deadlocks.
  • Distributed locks (a lease with a time-to-live, or an advisory lock) can expire while their holder still works, so correctness needs a fencing token the storage checks. Prefer no lock: idempotent effects and unique constraints.
  • Eventual consistency, stated. After an asynchronous ingest, a document is found by keyword at once and by meaning only once embedded; say so in the API ("indexing").
  • One transaction for the change and its job or event (the outbox), never a write plus a separate publish that can half-fail.

  1. What does "effectively once" mean, and why is a retried model call still a problem?

    Answer

    At-least-once delivery plus an idempotent or transactional effect, so duplicates do not change the result. The model call itself is still made and billed again on every retry; idempotency protects the data, not the bill.

  2. What is full jitter, and what does it prevent?

    Answer

    Sleeping a random time between zero and the capped exponential backoff. It spreads out retries from clients that failed together, preventing a synchronized retry storm when a dependency recovers.

  3. Retry, circuit breaker, bulkhead: what does each protect against?

    Answer

    A retry recovers from a transient failure. A circuit breaker stops calling a dependency that keeps failing, sparing it and your workers. A bulkhead isolates workloads so one cannot exhaust capacity another needs.

Data engineering for AI

A model answers from whatever data arrived, so the data path to an AI feature needs the same discipline as the code path: contracts, quality checks, lineage, freshness targets, idempotent backfills, and evaluation data treated as data.

At a glance

Questions

  1. What is usually the riskiest assumption in an AI project, and how is it tested?

    Answer

    That the model can do the task well enough on real data. It is tested first, with a short spike and a small eval set of realistic cases, before anything is built around it.

  2. Product wants an agent in three weeks; engineering estimates eight. What do you do?

    Answer

    Ask what the date is for and what must work on day one; cut autonomy and scope (a workflow or read-only tools, one use case, one data source, internal users), ship the narrowest end-to-end slice behind a flag with a person approving any action, and state the risks.   3. Where does AI work usually slip against an estimate?

    Answer

    Between "works in the demo" and "passes the evals on real data", and in approvals with long lead times: security review, data-processing terms, model access.

Working with AI coding agents

A coding agent is a fast, capable newcomer that never gets tired and is sometimes confidently wrong; teams get the speed safely by giving it a written contract in the repository, a plan-implement-verify loop, small changes, and a human who reviews, merges and owns the result.

At a glance
  • The loop: plan, review the plan, implement, verify with tests, types and lint, and write down what was learned.
  • State the goal as an outcome with its constraints, not as a method.
  • An instructions file in the repository is the contract: commands, conventions and prohibitions. When an agent gets something wrong twice, the fix goes there.
  • Tests are the real gate: untested generated code is as unmergeable as untested human code, and a test must never be loosened to get green.
  • Small pull requests, one concern each; a human merges and owns what was merged.

Questions

  1. Why should a prompt to a coding agent state an outcome rather than a method?

    Answer

    An outcome with constraints ("the health check survives a database restart") lets the agent find the right change and gives a test for success; a method ("add a try/except at line 40") encodes a guess and cannot be verified against the real goal.

  2. What failure patterns do you look for when reviewing agent-written code?

    Answer

    Invented APIs or parameters, silently swallowed exceptions, clever one-liners nobody can maintain, tests that assert something trivial, and checks weakened to make the change pass.

  3. An agent keeps making the same mistake. Where does the fix go?

    Answer

    In the repository's instructions file, which every session reads, so the correction is permanent and visible to people too.

The unit a document is split into for retrieval: both what the search matches and what the model reads. Chapter 4

Stops calling a dependency after repeated failures, lets one trial through after a cooldown, and closes again on success. Chapter 11

A component with more rights than its caller, used by the caller (or by text that steers a model) to act beyond the caller's own rights. Chapter 6

The most tokens, input and output together, a model attends to at once; hidden reasoning spends it too. Chapter 2

An agreed, versioned schema with meanings and freshness between a producing team and its consumers. Chapter 14

Where a job goes after its last allowed attempt, with its last error, for a person to fix and redrive. Chapter 11

The phase that writes one token per forward pass; memory-bandwidth-bound; sets tokens per second. Chapter 2
Embedding
A vector standing for a token inside a model, or for a whole text from an embedding model; similar meanings point in similar directions. Chapter 4

A record, stored with every vector, of the model, dimensions and document prefix that made it; vectors with different keys are not comparable. Chapter 4

Deciding that two names are one thing, or one name is two, in a knowledge graph. Chapter 5
Eval
A versioned case run against the real model and prompt, often many times, measured as a pass rate rather than pass or fail. Chapter 7

A test of whether two pass rates really differ; used to decide whether a case regressed against the baseline. Chapter 7

Retry backoff that sleeps a random time between zero and the capped exponential delay, so clients that failed together do not retry together. Chapter 11
Gateway (model)
A service between applications and model backends: authentication, request and token limits, routing, fallback, logging and cost tracking. Chapter 3

Retrieval that finds entry points by similarity and then follows relationships in a knowledge graph. Chapter 5
HNSW
A layered-graph approximate nearest-neighbor index: fast, memory-hungry, with build-time and query-time width parameters. Chapter 4

Keyword and semantic retrieval run together and merged, usually by reciprocal rank fusion. Chapter 4

Idempotency
The property that repeating an operation has the same effect as doing it once; with at-least-once delivery, it makes processing effectively once. Chapter 11
Judge
A second model asked a yes-or-no question about an answer, for what no deterministic check can decide. Chapter 7

Entities as nodes and typed relationships as edges, stored as subject, predicate, object facts. Chapter 5

The model's raw score for one candidate next token; softmax turns logits into probabilities. Chapter 2

Bronze (raw, kept), silver (cleaned, typed) and gold (the modeled tables) in a lakehouse. Chapter 13

Mean reciprocal rank: the average of 1 ÷ the rank of the first relevant result. Chapter 4

A setting that stops an AI feature in seconds on every server, without a deploy, while the rest of the service keeps working. Chapter 12

A filter applied after an approximate index's candidate list, which can leave a small tenant with no results and no error. Chapter 4

The phase that reads the whole prompt in one parallel pass and builds the KV cache; compute-bound; sets time to first token. Chapter 2

A provider's discount for a long, identical prompt prefix it has seen recently. Chapter 10

Text that tries to instruct the model: typed by the user (direct) or inside content the model reads for them (indirect). Chapter 9

Storing weights in fewer bits (8 or 4) to save memory and speed decode, at an uneven cost in quality. Chapter 3

A model that spends hidden output tokens thinking before it answers; the thinking counts against the output limit and is billed. Chapter 2

Whether a relevant item is in the top k results; it bounds what generation can use. Chapter 4

Replacing credentials in text before any model call, recognized by name, format or position. Chapter 9

A divisor applied to logits before sampling: below 1 sharpens toward the likeliest token, above 1 flattens. Chapter 2

How long until the first token arrives: the provider starting, then any reasoning, before the answer's first token. Chapter 2

The subword unit a model reads and writes; prices, limits and speed are counted in tokens. Chapter 2
