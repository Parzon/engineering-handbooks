Part I · What changed

From laptop to production

A change now travels one automated path: a pipeline reviews and tests it, builds it once into an immutable image, and deploys it by declaring which version should run, so a rollback is the same operation as a release.

At a glance
  • Every change goes through a pull request, automated checks and a review before it reaches the main branch.
  • A release is a version tag. It produces one image per component, built once and never rebuilt for another environment.
  • Environments differ only in configuration. The bytes tested in staging are the bytes production runs.
  • Deploying means "run version X". Rolling back means "run the previous version" through the same pipeline.
  • Infrastructure is code in the same repository, changed through pull requests like everything else.

The path a change takes

The figure below is the path the reference service actually uses, end to end. A developer's only actions are opening a pull request, merging it once it is reviewed and green, and pushing a version tag. Everything after the tag is automated, gated and reversible. Each stage is a chapter of this handbook.

Three properties make this path trustworthy, and the rest of the handbook explains how each is achieved.

  • Everything is reviewed. Code, infrastructure, pipeline definitions and even accepted security risks change only through pull requests.
  • Everything is reproducible. The release builds from locked dependencies and pinned base images. The infrastructure is rebuilt from code, and a drift check reports any change made by hand.
  • Everything is reversible. Releases roll forward and back through the same deploy, and database changes are written so the previous release keeps working.

One artifact, promoted through environments

The single most important rule on the path is build once, promote the same artifact. A release builds each component exactly once. Staging, production and any other environment then run those same bytes, identified by a version tag and, underneath it, a content digest that cannot change. Only the configuration differs: addresses, limits and secrets arrive from the environment at runtime.

Two consequences follow. A version must name exact bytes, so nothing is ever deployed as latest: two pulls of latest can be different code, and a rollback has no name to return to. And a host never builds from source: building on a server needs compilers and internet access there, and two hosts building the same commit can still differ, because a package was republished or a base image patched in between.

In the repo.github/workflows/release.ymlthe release, described at the top of its own workflow

Pipelines are files in .github/workflows/, reviewed like code. The release workflow opens with a comment that states its whole contract: what a tag publishes, under which names, for which processors, and what happens before the release notes are written.

  • One tag produces three image names, the exact version, the minor line and the commit, and moves latest, which nothing here deploys: the comment says so.
  • It tests what it published, not what it built: it pulls the release on both processor types and runs the stack from it.
  • The same builds run, without pushing, on any pull request that changes their inputs, so a broken release build is caught before the tag.

Questions

  1. Why should staging and production run the same image rather than each building from the same commit?

    Answer

    Because a build is not reproducible bit for bit: packages get republished and base images patched between builds. Running the same image, identified by its digest, means what was tested is exactly what runs.

  2. What is the difference between a release and a deploy in this path?

    Answer

    A release is a version tag that builds, scans and publishes images once. A deploy tells an environment to run a particular released version. One release can be deployed many times, to many environments, and an older one can be deployed again as a rollback.

  3. Why is latest never deployed?

    Answer

    It is a movable label: two pulls can return different code, and there is no name to roll back to. A deploy must name exact bytes.

  4. What makes a rollback safe when the release being undone changed the database?

    Answer

    Writing migrations so they only add (expand) before anything is removed (contract), so the previous release still runs on the newer schema. A rollback then deploys the older code and leaves the schema alone. Chapter 13 covers it.

Part II · Source and build

Git and the pull request

Git stores immutable snapshots and moves labels between them, and the pull request is the single gate through which every change, reviewed and tested, reaches the always-deployable main branch.

At a glance
  • Git's model is small: commits never change, and branches, tags and HEAD are labels pointing at commits.
  • A file lives in three places: your working tree, the staging area (the next commit), and the last commit.
  • Trunk-based development is the default for services: one main branch, always deployable, fed by short-lived branches.
  • Branch protection turns the pull request into a gate: required checks, required reviews, and a linear history.
  • An issue number threads through the branch, the commits, the pull request and the release, so every change can be traced to its reason.
Then and now
ThenNowWhy it changed
Centralized version control: one server, locks, commits straight to trunkGit: every clone is a full copy, and changes arrive through pull requestsCheap branches and offline work, with review built into the flow.
Long-lived feature and release branches (GitFlow)Trunk-based: branches live for hours or days, main is always deployableLong branches drift and make merges painful; services ship continuously.

The model: snapshots and labels

Most confusion with Git disappears once the model is clear. A commit is a snapshot of the whole project plus a pointer to its parent commit. Its identifier is a hash of both, so a commit can never change: change anything and you have a different commit. A branch is a label pointing at one commit, which moves forward when you commit. A tag is a label that never moves. HEAD is where you are.

A remote is simply another copy of the same database. fetch downloads its new commits and moves your origin/main label. pull is a fetch followed by a merge. push uploads your commits and asks the remote to move its branch label, which it refuses unless your history contains its history.

One practical consequence matters for operations: a running service reads the disk, not Git. On restart it loads whatever the working tree holds, including uncommitted edits or half-resolved conflict markers. That is why a production host is never a developer's checkout: a deploy puts a specific, built release on it (Chapter 3).

Three places a file lives

In git status --short the left column compares the staging area with the last commit, and the right column compares the working tree with the staging area. MM means "staged, then edited again": add it again. Untracked files appear in neither diff, which is how a new file gets forgotten.

Merge, rebase and squash

Three ways to bring a branch's work into main produce three different histories. Teams pick one per repository; the reference service squash-merges and requires a linear history.

A conflict looks the same in all three. Git writes both versions into the file between <<<<<<<, ======= and >>>>>>> markers; you edit the file to its final form, stage it and continue, or abort and start again. If a commit you rewrote disappears, git reflog still knows where every label pointed recently.

Trunk-based development

For a service that deploys continuously, the default is trunk-based development: one permanent branch, main, always deployable, and short branches that live for hours or days, each merged through a pull request and then deleted. GitHub flow is the same idea. GitFlow, with its develop, release/* and hotfix/* branches, exists for software shipped in several supported versions at once, such as installed products. Recognize it; do not pick it for a service.

The pull request as a gate

The pull request is where a change is explained, verified and reviewed. Its value depends on the rules around it, and on GitHub those rules are branch protection. On the reference repository, main requires:

  • six green checks: lint, test-api, build, security, web-build and e2e, on a branch that is up to date with main;
  • one approving review, including one from the code owners of every path touched, with approvals dismissed when new commits arrive;
  • a linear history, so every change lands as one squashed commit.

Code owners say whose approval a path needs. The pull request template asks the author for the evidence a reviewer needs, so verification is written down rather than assumed.

In the repo.github/pull_request_template.mdand.github/CODEOWNERS

Every new pull request opens with this template already filled in as its description. The checklist asks for exactly the evidence that would have caught past failures.

  • "How I verified it" wants commands and numbers, not "tested locally".
  • The checklist asks about failure paths, backward-compatible migrations and bounded metric labels: the three things most often missed.
  • The code owners file treats accepting a vulnerability or exempting a secret as decisions that need an owner's review, like an architecture decision.

Habits that keep history useful

  • Branch names as type/issue-short-description, such as fix/31-pool-leak. Create the branch before the first edit.
  • Commit messages in the Conventional Commits style (feat:, fix:, docs:), with an imperative subject and the reason in the body.
  • Small pull requests with one concern each. This matters more with AI coding tools, which produce large diffs quickly; a large diff gets skimmed, not reviewed.
  • Never commit secrets, generated output or environments (.venv, node_modules, build directories). A secret that reaches a commit is rotated, not just deleted: on a public repository it was copied the moment it was pushed.

Going deeper Recovering from the usual mistakes

A commit on the wrong branch. Create the right branch where you are (it keeps the commit), then move the wrong branch back one commit. Uncommitted work travels with you when you switch branches, so switching before committing is often enough.

A rebase gone wrong. git reflog lists every position HEAD has had. Reset the branch to the entry before the rebase.

Files deleted from disk by a branch switch. If they were committed on any branch, git show branch:path prints them back. Untracked files are never touched by a switch.

A secret pushed to a public repository. Rotate it first. Rewriting history afterwards removes it from the repository, but not from forks, caches and anyone who already cloned.

Questions

  1. Why can a commit never change, while a branch changes all the time?

    Answer

    A commit's ID is a hash of its snapshot and its parent, so any change makes a different commit. A branch is only a label pointing at a commit, and it moves forward with each new commit.

  2. When is rebasing safe, and when is it not?

    Answer

    It is safe on your own commits that nobody else has. It is unsafe on commits others already have, because rebasing gives them new IDs and their copies no longer match.

  3. What does a squash merge give a team, and what does it cost?

    Answer

    One commit per change on main, so one revert undoes a whole feature and the history reads as a list of changes. The small commits are no longer on main, but they remain visible in the pull request.

  4. Which branch protection settings turn a pull request into a real gate?

    Answer

    Required status checks on an up-to-date branch, required reviews including code owners, stale approvals dismissed on new commits, and a linear history. Without them, a pull request is only a suggestion.

  5. Why should a production server never run from a Git checkout?

    Answer

    A service reads its files from disk, including uncommitted edits and conflict markers, and a checkout can drift from any recorded version. A deploy should place a specific built release on the host.

CI/CD and artifacts

Continuous integration checks every change before it can merge; continuous delivery turns a tagged commit into immutable, versioned images and deploys exactly those, so what was tested is what runs.

At a glance
  • CI is the merge gate: lint, types, unit and integration tests, an image check, scans and browser tests, on every pull request.
  • CD builds an artifact, pushes it to a registry and deploys it. The artifact is a container image named by version and identified by a digest.
  • Four rules: build once and promote; artifacts are immutable; environments differ only in configuration; rollback is deploying the previous artifact.
  • A tag can move; a digest cannot. Deploy by exact version from a registry with immutable tags, or by digest.
  • One tag can serve several processor types through a multi-architecture index, and each architecture is built natively.

Continuous integration: the merge gate

On every pull request, the reference service runs six jobs in parallel on fresh machines. All six are required by branch protection (Chapter 2), so a pull request cannot merge until they pass. Each job is the same command a developer can run locally, which keeps "it passed on my machine" and "it passed in CI" the same statement.

Two kinds of test sit in this gate, and they catch different bugs. A unit test checks one function in isolation, in milliseconds. An integration test runs real parts together, such as the api against a real Postgres, connection pooler and cache, and catches wiring bugs a unit test cannot see. The test-api job builds a throwaway stack for the integration tests and deletes it afterwards. The e2e job goes one step further and drives a real browser through the production-shaped stack, which once caught a bug no unit test could reproduce. Handbook 2 covers testing in depth.

In the repo.github/workflows/ci.yml

The top of the CI workflow sets three rules that apply to every job.

  • Every third-party action is pinned to a full commit SHA, not a version tag, because a tag can be moved to malicious code. Chapter 4 explains why.

Where CI runs, and what it costs

GitHub Actions runs each job on a fresh, GitHub-hosted virtual machine, billed by the minute. Three habits keep the bill and the wait down: cache dependency downloads keyed on the lockfile, run expensive workflows only when their inputs change (path filters), and cancel superseded runs. A self-hosted runner executes whatever a workflow tells it to. Never attach one to a public repository that accepts pull requests from outside: a stranger's pull request would run code on your machine.

Continuous delivery: a tag becomes a release

A release starts when someone pushes a version tag, such as v0.8.2, to a commit on main. Versions follow semantic versioning: MAJOR.MINOR.PATCH, where the major number changes for a breaking change, the minor for a compatible feature, and the patch for a fix. Teams choose between deploying every merge to main (continuous deployment) and deploying on a tag (continuous delivery). The reference service deploys on a tag.

Each step guards against a specific failure. Checking that the tag points at a commit on main stops anyone releasing code that never passed review. Scanning again at release catches vulnerabilities published after the merge. Testing the published images, rather than the build outputs, proves the registry holds what the team thinks it holds.

In the repo.github/workflows/release.ymlthe release's guards and its build outputs

Tags, digests and multi-architecture images

An image is the immutable build output, identified by a digest: a hash of its content, such as sha256:fcbc59d1…. A tag is a movable label, like a Git branch. The release workflow moves 0.8 on every 0.8.x release on purpose; a re-push can move any tag unless the registry forbids it. So deploy an exact version from a registry with immutable tags, or deploy by digest, and never deploy latest or a moving tag such as 0.8.

The reference release builds each architecture on a native runner (an Arm machine for arm64) rather than emulating one on the other. Emulated builds are slow and occasionally behave differently. Each build pushes its image by digest, and a final job joins the digests under the version tags.

When the release was copied from GitHub's registry to Amazon ECR, the index digest in ECR was identical to the one on GitHub: the same bytes in a second place. Pushing a different image over an existing tag in ECR was then refused, because the repositories have immutable tags. A tag in that registry always names the same bytes.

Questions

  1. What is the difference between a unit test and an integration test, and why does CI run both?

    Answer

    A unit test checks one function in isolation and is fast. An integration test runs real components together and catches wiring bugs, such as a wrong connection setting or a missing migration. Each catches failures the other cannot.

  2. Why does the release workflow test the images it published rather than the ones it built?

    Answer

    Because what matters is what hosts will pull. Testing the published images, on each architecture, proves the registry holds working images under the release tags.

  3. What is the difference between a tag and a digest, and which should a deploy use?

    Answer

    A tag is a movable label; a digest is a hash of the content and never changes. Deploy by digest, or by an exact version tag in a registry that makes tags immutable. Never by latest or a tag that is moved on purpose, such as a minor line.

  4. Why might a team build arm64 images at all?

    Answer

    Arm servers such as AWS Graviton cost less for the same work, and many developer laptops are Arm. One tag with both images lets every host pull the right one.

  5. What does build provenance answer that a version number does not?

    Answer

    Which commit and which workflow run produced this exact image. A version number is only a label someone chose; provenance is a signed record stored with the image.

What you ship but did not write

A small service's own code is a thin layer on top of a much larger stack. Each layer has its own way of changing under you, and its own control.

    Answer

    Rotate the key, so the leaked value stops working. Removing it from history comes second: on a public repository it may already have been copied.

Identity without keys

People, pipelines and running services each prove who they are to a trusted identity provider and receive credentials that expire on their own, so there is no permanent key anywhere to leak.

At a glance
  • Three kinds of caller need cloud access: people, CI pipelines and workloads. Each now gets temporary credentials, by a different route.
  • People sign in once a day through single sign-on with MFA. Their sessions end by themselves.
  • Pipelines use OIDC federation: the CI platform signs a token that says which job is running, and the cloud exchanges it for credentials that last an hour.
  • Workloads use a role attached to the compute. The platform hands out and rotates the credentials.
  • The trust policy is the security boundary. It is an exact match on claims, so write it from the token you actually receive, not from an example.

Three callers, three routes

The old model gave every caller a long-lived secret: a password, an access key, an SSH key. Each one had to be stored somewhere, rotated by someone, and revoked when a person left. The modern model replaces all of them with the same pattern. A caller proves who it is to a system that already knows it, and receives credentials with a short, fixed lifetime.

The rest of this chapter takes each lane in turn. Pipelines get the most space, because that is where the change is newest and where the configuration is easiest to get subtly wrong.

People: single sign-on, and no standing access to production

An engineer signs in once a day through the company's identity provider (Okta, Microsoft Entra ID and others), with MFA. AWS IAM Identity Center maps the groups that provider asserts to roles in each account: development, staging, production. The command-line tools then fetch short-lived role credentials as needed. When the sign-in session ends, usually after a working day, everything stops working until the person signs in again. A stolen laptop's credentials die on their own.

Production adds one more rule: people do not deploy by hand. The pipeline deploys through its own role. People are read-only by default and get elevated access only on request, for a fixed time, and every use of it is recorded. This is often called break-glass or just-in-time access.

The reference build used a single throwaway account, so it signed in with the simpler aws login. The idea is the same: a browser sign-in that yields temporary credentials, and no access keys on disk. Root user access keys were never created.

Pipelines: OIDC federation

A CI job is the caller with the most power and the least supervision: it runs automatically, on shared infrastructure, and can push images or change infrastructure. It also cannot type a password. The old answer was an access key stored in the CI system's secrets. The modern answer is OpenID Connect (OIDC) federation: the CI platform vouches for the job, and the cloud decides whether to trust that.

Four pieces make it work:

  1. The job asks for a token. GitHub signs a JSON Web Token (JWT) for each job that has permissions: id-token: write. Without that line, no token is issued.
  2. The token describes the job. Its iss (issuer) is GitHub's token service, its aud (audience) is sts.amazonaws.com, and its sub (subject) names the repository and either the git ref that triggered the job or the GitHub environment the job runs in.
  3. AWS trusts the issuer once per account. An IAM OIDC provider entry tells AWS to accept tokens signed by GitHub's published keys.
  4. A role decides which jobs it will serve. Its trust policy allows sts:AssumeRoleWithWebIdentity only when aud and sub match. A different repository, branch, tag or environment is refused.

Workloads: roles attached to the compute

A running service should never hold a key either. On AWS, a role is attached to the compute itself: a task role for an ECS task, an instance profile for an EC2 VM. The platform serves that role's credentials to the code at runtime and rotates them. Your code, using the standard AWS SDK, picks them up without any configuration.

ECS has two roles per task, and mixing them up is a common mistake. The task execution role is used by ECS itself, before your code runs, to pull the image and inject secrets. The task role is what your code may call once it is running, such as S3 or a queue. A service that needs no AWS API at runtime needs no task role at all.

Application secrets that are not AWS credentials, such as a database password or a model provider's API key, follow the same principle. They are generated by Secrets Manager, read by ECS when the task starts, and handed to the container as environment variables. They never appear in the image, the task definition, the CloudFormation template or the repository.

A case from the reference build: the test that proved nothing

When the image-push role was first set up, the plan was to prove the trust policy worked by breaking it on purpose. The policy was edited to name the wrong repository, a release tag was pushed, and the job failed with Not authorized to perform sts:AssumeRoleWithWebIdentity, as expected. Then the correct repository name was restored and only the failed jobs were re-run. They failed again.

The policy had been written in the subject format most documentation shows, repo:owner/name:…. This repository's tokens use a form that embeds the numeric owner and repository IDs, which survives renames and stops a deleted-and-recreated repository with the same name from inheriting the trust. Reading the repository's OIDC subject setting showed the real value. With the prefix fixed, all three image copies succeeded, and the digests in ECR matched the ones published to GitHub's registry: the same bytes in a second place.

Two habits come out of this. Check the real claims first, before blaming anything else, because the error never says which condition failed. And re-run failed jobs rather than cutting a new release: it is faster, and it tests exactly the same thing.

Going deeper What a trust policy can and cannot see

GitHub's token carries many claims: the repository and its owner, the ref, the commit, the workflow file, the environment, the event that triggered the run. AWS IAM can write conditions on only a few of them, chiefly aud and sub. That is why the subject's format matters so much, and why GitHub lets a repository or organization customize which claims are combined into the subject. Including the workflow file in the subject, for example, lets a role trust one specific workflow rather than any job in the repository.

The same customization setting is what produced the immutable form seen in the case above. Reading it, rather than assuming the default, is the reliable way to know what the policy must match.

StringLike allows the wildcards * and ?; StringEquals does not. Use the exact form wherever there is nothing variable to allow, as the deploy role does, so a typo cannot widen the trust.

One OIDC provider entry per issuer is allowed in each account. Several roles can trust the same provider, each with its own conditions, which is how one account serves several repositories and environments.

Questions

  1. What does a CI job need before it can obtain cloud credentials through OIDC, and what does it receive?

    Answer

    The job needs permissions: id-token: write, so the CI platform will sign a token for it, and the cloud account needs an OIDC provider entry that trusts that platform. It presents the token to AWS STS and receives temporary credentials for a role, valid here for at most one hour.

  2. Why does the deploy role trust a GitHub environment rather than a tag or branch?

    Answer

    A job that names an environment gets a subject ending in :environment:NAME. Trusting that subject means GitHub's environment protection rules, such as allowed branches and required reviewers, decide which jobs can reach production. Approvals can then change without editing AWS.

  3. You break a trust policy on purpose and the job fails. What must you check before concluding that the policy works?

    Answer

    That the correct policy actually passes. A failure only proves something if a success was seen first. Otherwise the policy may never have matched, as in the case in this chapter.

  4. What is the difference between an ECS task execution role and a task role?

    Answer

    The execution role is used by ECS before your code runs: to pull the image and to inject secrets. The task role is the identity your code uses to call AWS services while it runs. A task that calls no AWS API at runtime needs no task role.

  5. Why is removing SSH access a security improvement rather than only an inconvenience?

    Answer

    There is no key to leak, no open port to attack, and every command run through Session Manager or Run Command is authorized by IAM and recorded in CloudTrail against a named person.

  6. Which permission in the image-push role cannot be limited to the three repositories, and how is that handled?

    Answer

    ecr:GetAuthorizationToken, which is account-wide by design. It is granted on * with a comment saying why, while push and pull are granted only on the three repositories.

The deployment ladder, and one VM done properly

Deployment has climbed from copying files by hand to declaring the desired state and letting a platform converge on it, and a single, well-built virtual machine is still a sound first rung if it keeps the habits that make the next rung easy.

At a glance
  • Each rung of the ladder hands one more job to automation: copying, then running, then replacing, then scheduling, then owning the machines.
  • One VM is a good start for a pilot: one host, one script, logs in one place. What matters is that it runs released images, never a checkout.
  • A deploy on one host can drop no requests: start the new version beside the old one, wait until it is healthy, then drain the old one.
  • A proper VM has no SSH key and no open port 22, pulls images with its own role, and is rebuilt from code rather than patched by hand.
  • Keep the rule "CI builds one image per version; deploying means run this version", and moving to a managed platform later is small.

The ladder

Rungs 0 and 1 are where many teams started: log in, copy, restart. Rung 2 is the first that is reproducible, because the server runs an image built by CI. Rung 3 adds capacity and redundancy but leaves N machines to update without taking the fleet down. Rung 4 is the big change in thinking: instead of running commands, you declare what should be running, "two copies of version 0.8.2", and an orchestrator such as Kubernetes or ECS works continuously to make reality match, replacing a few copies at a time. Rung 5 removes the machines from view entirely.

"Serverless" does not mean one very reliable server. It means many small, disposable units that the platform replaces when they are unhealthy. Fargate and Cloud Run run your container images; Lambda runs a zip file or an image in lightweight virtual machines. A Python virtual environment isolates packages but not the operating system's libraries or the interpreter build, which is why a platform that wants an image gains nothing from a virtual environment alone.

One VM, without ceremony

A single VM is the right first home for a pilot with few users, where a short night-time maintenance window is acceptable and the team is new to operations. Where ECS asks a new team to learn roles, task definitions, load balancers and networking at once, a VM is one box, one script and logs in one place. The reference service ran on a VM before it ran on ECS, with the same images.

  • The image goes to a registry, not to Git. The VM pulls it by version, authenticated by its own role on AWS, and never builds anything.
  • The deploy definition matches the version. The compose file and deploy script must match the images, so they come from the same release: shipped by CI with each deploy, or checked out at the release tag. Never a working copy someone edited.
  • The deploy script does five things: record the version, pull it, run migrations as a one-off container, start the new version, check its health and go back to the previous version if it fails.
  • Rollback is the same script with the previous version.

Agents on hosts, and immutable infrastructure

A monitoring or log-shipping agent is a small background program that works for a remote service; nothing to do with AI agents. It is needed because the container runtime keeps only each container's standard output, and host metrics such as CPU and disk are a separate job. Often the runtime's logging driver is enough on its own, sending container output straight to CloudWatch.

How an agent reaches a host depends on the rung. On plain VMs it is baked into a golden image built by a tool such as Packer, or installed by the first-boot script. On ECS or Cloud Run it is a setting of the service, with no host to touch. On Kubernetes it is a DaemonSet: one copy per node. In every case the host is rebuilt from a versioned definition, never patched by hand. That is what immutable infrastructure means.

Infrastructure as code

Infrastructure as code describes networks, servers, databases and permissions in reviewed files, and a tool works out and applies the difference between that description and what exists, so environments can be rebuilt, reviewed and audited like software.

At a glance

  • Always look at the difference before applying it: cdk diff or terraform plan, ideally in the pull request.
  • CDK writes AWS infrastructure in a real programming language and hands it to CloudFormation. Terraform uses its own language and reaches any cloud through providers.
  • A change made by hand in the console is drift: detect it, and fix it through the code, or the next deploy will silently undo it.
  • Infrastructure changes go through pull requests, and CI applies them with keyless credentials.

How the tools work

Every infrastructure-as-code tool has the same three parts: a description of the desired end state, a record of what it has already created, and an engine that turns the difference into API calls. The tools differ in the language you write and in where the record lives.

CDK (AWS Cloud Development Kit) lets you write infrastructure in Python, TypeScript and other languages. It synthesizes a CloudFormation template, and CloudFormation creates the resources and remembers them as a stack. Because AWS keeps that record, deleting the stack removes exactly what it created, and drift detection compares reality with it.

Terraform uses its own declarative language, HCL, and reaches any cloud or service through providers. It keeps its record in a state file. That file must live remotely (an S3 bucket, an Azure storage blob, a Google Cloud bucket) with a lock, so two people applying at once cannot corrupt it, and it must be protected: it can contain secrets. Terraform moved to the Business Source License; OpenTofu is its open-source fork. Pulumi offers real programming languages across clouds.

Drift: when reality and the code disagree

To test scaling, the reference ECS service was scaled from one task to two with a single command-line call: a change made outside the code. CloudFormation's drift detection reported it precisely. Left alone, the next deploy would have set the count back to one without anyone noticing.

The last mile: first-boot scripts

A virtual machine still needs something to run on its first boot. cloud-init (passed as user_data on AWS) runs once, at first boot: install the container runtime, log in to the registry with the machine's role, pull a specific version, run it with a restart policy, fetch secrets at runtime. It does not run again on later deploys. A new version either replaces instances (a new launch configuration in an Auto Scaling group) or runs a command on the existing ones through Run Command. The mature form bakes the runtime and agents into a golden image and keeps the first-boot script to "pull and run".

Networking on AWS

An AWS network is built from layers you compose (a private network, subnets that a route table makes public or private, gateways for traffic in and out, and firewalls that name each other), and the safest designs leave only the load balancer reachable from the internet.

At a glance
  • A VPC is your own isolated network in one region. A subnet is a slice of it in one availability zone.
  • A subnet is public or private only because of its route table: public means it has a route to an internet gateway.
  • A NAT gateway lets private subnets reach out without being reachable. It costs money per hour and per gigabyte.
  • Security groups are stateful allow-lists on each resource, and can name other security groups instead of IP addresses: the load balancer may reach the api, and only the api may reach the database.
  • Put the database in a subnet with no route to the internet at all, so a single security group mistake cannot expose it.

A home router, split into AWS resources

A home router does three jobs in one box, and AWS turns each into a separate resource you configure on its own. The mapping is a good way in.

The parts

  • VPC. Your own isolated network, spanning one region, with an address range written in CIDR notation.
  • Subnets. Slices of that range, each pinned to one availability zone. Routing is decided per subnet by its route table, which is the real reason subnets exist.   • NAT gateway. Lets private subnets make outbound connections, to a model provider's API or a package mirror, without accepting inbound ones. It is billed per hour and per gigabyte processed.
  • Security groups. Stateful, per-resource, default-deny allow-lists. Stateful means a reply to an allowed request is allowed automatically. A rule can name another security group as its source.
  • Network ACLs. A coarser, stateless filter per subnet. Most teams leave them at their defaults unless compliance requires more.

The reference network

The reference stack's network is deliberately cheap, and the code says so. It has two zones with public subnets for the load balancer, the VM and the ECS tasks, and isolated subnets for the database, with no route to the internet in either direction. There is no NAT gateway, because nothing in a private subnet needs to reach out. Address ranges in CIDR notation

CIDR notation writes a range as an address and the number of fixed bits. 10.20.0.0/16 fixes the first 16 of 32 bits and leaves 16 free: 65,536 addresses. A smaller number after the slash is a bigger range. AWS reserves five addresses in every subnet, so a /24 holds 251 usable ones. A subnet's range caps how many resources it can hold (one address each, not one per connection), which matters for tasks that each get their own network interface.

Toward a production network

The production version of this design moves the tasks into private subnets with no public addresses. If a security team restricts outbound traffic, the model provider's API host must be on the allowed list, or every assistant request fails. The public DNS record points at the load balancer as an alias, never at an IP address, because the load balancer's addresses change.

At a glance

Rehearse the task locally first

Most cloud failures are configuration, and a Fargate task can be rehearsed on one machine before any money is spent: containers in a task share one network namespace, which docker run --network container:<first> reproduces, and a plain Postgres container with only an owner user stands in for RDS, which runs no setup scripts. The rehearsal for the reference build found four problems:

  • The production guard worked. With production settings the api refused to start: plain-HTTP cookies and a fake model. Without a domain or a model provider, both were honest exceptions, named one by one in a waiver setting rather than turned off.
  • The web image assumed Compose. Its nginx found the api through Docker's internal DNS, which Fargate does not have. On AWS the load balancer routes /api/* straight to the api and strips the prefix, and nginx only serves files.
  • A rollback trap. Rolling back across a migration made the migration tool fail on a revision it did not know. The migration step was taught to recognize that case and do a code-only rollback (Chapter 13).
  • Least privilege. A setup container creates the application's own database user, allowed to read and write rows but not to change the schema, and does it idempotently, because RDS will not run setup scripts.

Every new task migrates before it serves, which is simple, but tasks can start together (the first deploy starts two), and two migration runs at once collided: one failed. A release on ECS

  1. CI copies the release images to ECR, authenticating with an OIDC role (Chapter 5).
  2. The deploy registers a new task definition revision with the new image and updates the service.
  3. ECS starts new tasks beside the old ones, waits for the load balancer's health check, shifts traffic, and stops the old tasks, which finish their in-flight requests first.
  4. If the new tasks keep failing to start, the deployment circuit breaker rolls the service back to the previous revision, and the deploy fails.

Measured on the reference service, with a probe sending requests twice a second: a forward deploy took 3 minutes 17 seconds with 352 requests and none failed, and the deliberate bad release was rolled back in under 8 minutes while the old tasks kept serving. Kubernetes and EKS

Kubernetes is a portable orchestrator that keeps declared workloads running through a control loop, with a richer model than ECS (separate readiness and liveness, init containers, an ecosystem of controllers), at the price of a cluster someone must run and a standing cost.

At a glance
  • You declare objects (a Deployment of three replicas of an image); controllers continuously reconcile reality toward them.
  • The control plane (API server, etcd, scheduler, controllers) decides; the nodes run pods. Managed offerings such as EKS, GKE and AKS run the control plane for you.
  • Readiness and liveness are separate probes: one controls traffic, the other restarts containers. ECS has only one signal.
  • Every pod gets a routable IP and services get DNS names, so containers on different hosts find each other the way Compose services do on one host.
  • Pick ECS for a few AWS-only services and a small team; pick Kubernetes for many services, a platform team, portability, or its ecosystem.

The model: declare, then reconcile

Kubernetes inverts the deploy script. Instead of a sequence of commands, you submit objects that describe the end state: a Deployment that says "three replicas of this image", a Service that gives them a stable name, a ConfigMap and Secret for configuration. Controllers then run a loop forever: observe the cluster, compare it with the objects, act on the difference. A node dies, three replicas become two, and the loop starts a third elsewhere without anyone being paged.

Two probes, two questions

The biggest practical difference from ECS for the reference service is health. Kubernetes asks two separate questions. A readiness probe decides whether a pod receives traffic: when it fails, the pod is removed from its Service's endpoints, but keeps running. A liveness probe decides whether the container is stuck: when it fails, the container is restarted. The reference api was written for exactly this split, with /ready and /health.

Questions

  1. What is the reconcile loop, and why does it make deploy scripts unnecessary?

    Answer

    Controllers repeatedly observe the cluster, compare it with the declared objects, and act on the difference. You change the declaration, and the controllers make it true, including after failures, so there is no script of steps to run.

  2. What happens to running workloads if the control plane fails?

    Answer

    Running pods keep running, because each node's kubelet carries on. Deploys, autoscaling and recovery from a dead node stop until the control plane is back.

  3. What is the difference between a readiness probe and a liveness probe?

    Answer

    Readiness decides whether a pod receives traffic; failing it removes the pod from rotation without restarting it. Liveness decides whether the container is stuck; failing it restarts the container.

  4. When would you choose EKS over ECS?

    Answer

    When there are many services and a platform team, when portability across clouds matters, when the Kubernetes ecosystem (operators, GitOps, a mesh) is needed, or when the organization already runs Kubernetes.

Three differences worth knowing

Revisions and traffic splitting

On Cloud Run and Container Apps, every deploy creates an immutable revision, and traffic is split between revisions by percentage. A canary (5% to the new revision) or a rollback (100% back to the old one) is a setting, not a redeploy. On ECS the equivalent is a rolling deployment with its circuit breaker, or blue/green deployments through CodeDeploy.

HTTPS out of the box

Cloud Run and Container Apps give each service an HTTPS address with a managed certificate. On AWS, a load balancer needs a certificate from ACM and a domain you control. That is why the reference build's AWS stage ran over plain HTTP, with that exception named explicitly in the service's production checks.

Scale to zero

Cloud Run and Container Apps can run no instance at all while a service is idle, and start one on the next request, at the cost of a cold start. A Fargate service keeps its minimum number of tasks running, and billing, at all times. For an internal tool used a few times a day, scale to zero changes the cost picture; for an interactive service, the cold start usually rules it out.

Terraform across clouds

The language, the plan-and-apply workflow and the state file are the same on every cloud, through each cloud's provider. The resources are not: an ECS service has no Azure twin with the same fields, so it is rewritten as a Container App. Remote state with a lock lives in an S3 bucket, an Azure storage blob (with a lease) or a Google Cloud bucket, and CI authenticates to each through that cloud's OIDC federation. Chapter 7 shows the same registry declared on all three.

How to say it

"The design is cloud-neutral: one image per version, configuration from the environment, workload identities, keyless CI, infrastructure as code. Moving clouds renames the pieces; Cloud Run and Container Apps would also give us revisions, HTTPS and scale to zero by default."

Questions

  1. How do Cloud Run and Container Apps make a rollback cheaper than a redeploy?

    Answer

    Every deploy is an immutable revision, and traffic is split between revisions by configuration. A rollback sets 100% of traffic back on the previous revision, without building or deploying anything.

  2. Why did the reference AWS build run over plain HTTP, when the same service on Cloud Run would not have?

    Answer

    An AWS load balancer needs a certificate for a domain you control, and the build had no domain. Cloud Run and Container Apps give each service a managed HTTPS address by default.

  3. What carries over between clouds in Terraform, and what does not?

    Answer

    The language, the plan-and-apply workflow and remote state carry over. The resource definitions do not: each cloud's resources are written for that cloud.

Case studies from a real deployment

The reference service was taken from container images to a load-balanced, autoscaled ECS deployment in nine measured stages, and each stage either proved a property or exposed a failure worth knowing about before it happens to you.

At a glance
  • Every stage ended in evidence: a digest compared, requests counted during a deploy, a metric read from the load balancer.
  • Most failures were configuration, and several were invisible until something was measured.
  • A client-side probe reported an outage that never happened: judge availability from server-side metrics.
  • The finished loop: one version tag, and the release is live on ECS 8 minutes 37 seconds later, with no failed requests.
  • The whole reference deployment, VM and ECS stacks included, cost about sixty cents of cloud time, because everything billed by the hour was torn down after each session.

The stages

Images: the same bytes in a second place

The release images already existed in GitHub's registry, built for two processor types. They were copied into ECR as whole multi-architecture indexes, and the index digest in ECR matched the original exactly. Then a deliberate test: pushing a different image over an existing version tag. ECR refused, because the repositories have immutable tags, and the digest behind the tag was unchanged. A tag in that registry always names the same bytes.

One surprise: the registry's scan-on-push never ran on the copied images. It fires for ordinary pushes, and the copy took another path. The lesson is general: scanning belongs in the pipeline, before publishing, not only in the registry (Chapter 4).

The first ECS deploy: two failures, both configuration

  • No export named … found. The new application stack referenced the image repositories, which needed new exports from the registry stack, and the deploy had been limited to the new stack alone. Cross-stack references are ordered dependencies: deploy the producer first (Chapter 7).
  • "No subnets exist in Availability Zones with sufficient capacity." The database instance type was listed as available in all three zones, yet two had no capacity at that moment. Capacity is per zone and temporary. An extra isolated subnet in the third zone fixed it without touching anything running (Chapter 8).

After those, the containers started in the designed order (setup, migrations, sidecars, then the api), the readiness endpoint reported the database and cache healthy and the identity provider degraded (there was none in this stage), and internal paths returned 404 at the load balancer as intended.

An outage that never happened

During the bad-release drill, a probe on a developer's machine sent a request twice a second and reported 15 failures. The timeline did not fit: failures began after the bad task was already gone and continued after the rollback. Splitting curl's timings showed why.

The whole loop, with no human step

With the deploy workflow in place, the only human action was pushing a version tag (the environment has since gained a required reviewer, so a release now also waits for one approval). Everything after it ran on its own: the release built, scanned, published and smoke-tested the images and copied them to ECR; the deploy workflow then ran in the gated environment, applied the infrastructure code with the new version, waited for ECS to be stable, and smoke-tested through the load balancer.

Three design choices made this loop safe to leave unattended. The infrastructure code always comes from main while the image comes from the release, so rolling the application back never rolls the infrastructure back. Deploys share a concurrency group without cancellation, so two deploys queue rather than race. And workflow inputs reach shell commands only through environment variables, never interpolated into the script text, which closes a script-injection route.

Environments, releases and rollback

Releasing safely means choosing how traffic moves to a new version, deciding in advance how each kind of change is undone, and reaching real users in stages that each end in something you can measure.

At a glance
  • Four ways to move traffic: rolling, canary, blue/green, and feature flags. They protect against different failures.
  • Every kind of change has its own rollback, chosen before shipping: code, schema, configuration, a feature, infrastructure.

  • Reaching users is a staged road (a real host, real sign-in, a real model, a pilot team, then everyone), and each stage has a "done when".

Four ways to move traffic

The reference service uses rolling deploys everywhere, and for subtle regressions it currently relies on "deploy, watch the dashboard for half an hour, roll back if needed", which works because rollbacks are cheap and cross migrations. The next steps, in order of effort, are a canary on one host (a second api service and a weighted upstream in nginx), then the platform's own traffic splitting with automatic analysis against the service's objectives.

Rollbacks roll back code, never the schema

During a rolling deploy, the old and new versions run at the same time against the same database. So a schema change cannot break either of them, and it is done in steps that each leave both versions working. This is the expand and contract pattern.

The rule produced one of the reference service's decision records, after a rollback failed. The procedure had been "deploy the previous tag", and the previous tag's migration tool had never heard of the revision the newer release applied. The deploy stopped before touching anything, so it failed safely, but rollback was impossible across any migration: exactly when a rollback is most likely needed.

Rollbacks roll back the code, never the schema

Problem
Rolling a release back to one with fewer migrations failed: the older migration tool could not find the database's current revision.
Decision
A deploy never reverses a migration. When the database is ahead of the image, it skips migrating, says so, and rolls out the older code on the newer schema. Reversing a migration is a separate, deliberate step, decided by a person, run with the newer image.
Rejected
Automatic downgrades: the least-tested code in any project, able to lose data, and run under pressure.

Cost, teardown and lessons learned

Cloud cost is a design property you can see per hour and per component, teardown is a procedure worth writing down and testing, and the small operational mistakes of a real build are the lessons most worth passing on.

At a glance

    Answer

    Public IPv4 addresses, the second-largest item. Production networks keep tasks on private addresses behind a load balancer, which also removes them from the internet.

  3. What should happen after a teardown fails halfway?

    Answer

    Finish it (for example by retaining resources that are already gone), check for leftovers, and fix the cause in code so the next teardown works.
