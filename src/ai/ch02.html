Part II · How models run

How a model produces text

A language model turns text into tokens, scores every possible next token, samples one, appends it and runs again; latency, cost, memory and the variability that evals must measure all follow from that loop.

At a glance
  • One forward pass per output token. Prices, limits and speed are all counted in tokens.
  • Two phases: prefill reads the prompt in parallel and sets the time to first token; decode writes one token at a time and sets tokens per second. A reasoning model also decodes its hidden thinking before the first answer token.
  • Sampling (temperature, top-p) is why the same prompt answers differently, and why evals repeat runs.
  • The context window holds input and output together; hidden reasoning spends the output budget too.
  • The KV cache holds every earlier token's keys and values in GPU memory, and caps how many requests fit at once.

The loop

Attention, at a lead's level

Each layer does two things to every token's vector: attention mixes in information from other tokens, then a feed-forward network transforms each vector on its own. For attention, each token's vector is projected into a query (what it is looking for), a key (what it contains) and a value (what it passes on). A token's output is the average of the values, weighted by how well its query matches each key. Several heads do this in parallel, each learning a different kind of relation.

Prefill and decode: two phases, two bottlenecks

The KV cache

Every layer keeps the keys and values of all tokens so far in GPU memory, so decode computes them only for the new token. Per sequence it takes roughly two (keys and values) × layers × KV heads × head size × bytes per value × tokens: gigabytes for long contexts. It limits how many requests fit on a GPU at once; in the reference measurements, eight parallel slots of a 20-billion-parameter model used 38 GB, most of it cache. Paged allocation, grouped-query attention (fewer KV heads, a property of the model) and a quantized cache shrink it, and prefix caching reuses the cache of a shared prompt prefix across requests, which is the self-hosted form of a provider's prompt caching (Chapter 10).

The context window, and reasoning tokens

In the repoapps/api/app/config.pyan output limit sized for hidden reasoning

Two settings for reasoning models, with the measurement behind each default in the comment.

  • The output limit includes hidden thinking, so a limit sized for visible answers produced empty ones.
  • The effort parameter is sent only when set: models without reasoning reject it, so a setting that suits one model breaks another.
  • The model client reports an empty answer as its own error, llm_empty_answer, with a metric and an alert on truncated answers.
    # For reasoning models (OpenAI's o-series and gpt-5, gpt-oss) the limit
    # includes their hidden thinking: measured with gpt-oss:20b at the default
    # effort, 3 of 5 answers spent all 800 tokens thinking and said nothing.
    llm_max_output_tokens: int = Field(800, ge=1)
    # Reasoning models only ("low" | "medium" | "high"): how much they think
    # before answering. Unset = not sent - other models reject the parameter.
    # gpt-oss:20b at "low": 65-308 tokens instead of 460-800.
    llm_reasoning_effort: Literal["low", "medium", "high"] | None = None

A bigger context window is not free: prefill time and cache memory grow with it, and models use the middle of a long context worst. Send only what the question needs, ordered so that the most important material is at the start or the end.

How to say it

"Time to first token is prefill, which grows with the prompt, plus, for a reasoning model, its hidden thinking; tokens per second is decode, which is memory-bound. Total is roughly TTFT plus output tokens over the decode rate."

"Reasoning tokens are output: they count against the limit and the bill, so an empty answer is an error we count and alert on."

Questions

  1. Which phase sets the time to first token, which sets tokens per second, and what makes each worse?

    Answer

    Prefill sets the time to first token and grows with the prompt's length; it is compute-bound. Decode sets tokens per second; it is memory-bandwidth-bound and slows as more streams share the GPU or the cache grows. For a reasoning model, the first answer token also waits for its hidden thinking, which grows with reasoning effort; the time to the first chunk is the closer measure of prefill.

  2. What does temperature do, and why do evals repeat runs?

    Answer

    It divides the logits before softmax: lower sharpens toward the likeliest token, higher flattens. Sampling from the distribution means the same prompt gives different answers, so a case's behavior is a rate, measured over many runs.

  3. What is the KV cache, and why does it limit concurrency?

    Answer

    The stored keys and values of every earlier token, per layer, so decode does not recompute them. It lives in GPU memory and grows with each sequence's length, so it caps how many sequences fit on a GPU at once.

  4. Why can a reasoning model return an empty answer?

    Answer

    Its hidden reasoning is output and counts against the output limit; with a small limit or high effort, it can spend the whole budget thinking before writing anything visible.
