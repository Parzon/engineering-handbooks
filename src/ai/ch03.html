Serving models

Serving a model is a trade between throughput, which is the cost, and per-stream speed, which is the user's experience; and an application stays free to change the model or the provider only if it reaches every model through one small seam.

At a glance
  • Batching runs several sequences per forward pass: total throughput rises a lot, and each stream slows, here to about half its speed at four at a time. Set concurrency against a per-stream latency target.
  • GPU memory holds the weights (parameters × bytes each) plus the KV cache, which grows with concurrency and context.
  • Quantization saves memory and speeds decode, and costs quality unevenly: evaluate the quantized model itself.
  • Replicas when the model fits on one GPU; tensor parallelism within a node when it does not; pipeline parallelism across nodes only when you must.
  • One OpenAI-compatible seam, a mock behind it for tests, and a gateway when several services share models and quotas.

Throughput and latency: batching

GPU memory, precision and loading

Loading copies the weights from disk to the GPU, which takes tens of seconds for a large model, so a cold start is a latency spike. Keep models resident and warm them before traffic: Ollama, for example, unloads a model after five idle minutes by default, so the first call after a pause pays the load. A model that does not fit spills to the CPU, very slowly, or must be split across GPUs. One failure is worth knowing about: in the reference build, a GPU container silently lost access to its GPU after a day of use and loaded models on the CPU instead, with no error anywhere. The only sign was that judge calls taking about a minute had not finished after ten; checking which processor a model is loaded on, and recreating the container, fixed it.

The serving architecture, and the seam

In the repoapps/api/app/llm.pyprovider failures, mapped to the service's own

The seam's error mapping. Routes and the prompt module see only these few typed errors, whichever provider answers.

  • Each error has a stable code that metrics, alerts and the browser key on: a timeout, rate limiting, unavailability, a rejected request.
  • A 400-class rejection is the service's own mistake (key, model name, parameters); retrying will not help, so it is not retried.
  • Failures can arrive mid-stream, after the response has started, which is why the stream carries its own error event (Handbook 2, Chapter 10).
def _provider_errors(what: str) -> Iterator[None]:
    """The SDK maps transport failures to its own exceptions, both before
    and during a stream; these become ours. Order matters: APITimeoutError
    is a subclass of APIConnectionError."""
    try:
        yield
    except openai.APITimeoutError as exc:
        raise LLMTimeout(f"{what} took too long to respond") from exc
    except openai.RateLimitError as exc:
        raise LLMRateLimited("the model provider is rate limiting us") from exc
    except (openai.APIConnectionError, openai.InternalServerError) as exc:
        raise LLMUnavailable("the model provider is unavailable") from exc
    except openai.APIStatusError as exc:
        # 400/401/403/404: our request or configuration is wrong (key,
        # model name, parameters) - retrying will not help.
        raise LLMError(f"the model provider rejected the request ({exc.status_code})") from exc
    except openai.APIError as exc:  # e.g. an error event inside the stream
        raise LLMUnavailable("the model provider failed mid-answer") from exc

One OpenAI-compatible model client behind a small seam, with a mock provider

Problem
Every project would otherwise wire a vendor SDK into its routes, with the SDK's defaults: a ten-minute read timeout and two retries.
Decision
One client for any OpenAI-compatible endpoint, with explicit timeouts (5 s to connect, 60 s of silence, 120 s per answer) and one retry; a mock server with switchable failures, rather than an in-process fake, so tests exercise the real HTTP and streaming path. Native SDKs and orchestration frameworks were rejected as the default seam.

Managed API or self-hosted?

How to say it

"Batching trades per-stream speed for throughput; we set concurrency against a latency target, and the KV cache caps it."

"Every model call goes through one OpenAI-compatible seam with typed errors and explicit timeouts, so a new provider or a gateway is a configuration change, plus an eval run."

Questions

  1. Why does batching raise throughput but slow each stream?

    Answer

    Decode is memory-bound: each forward pass reads all the weights. Batching reads them once for several sequences, so total tokens per second rises; each sequence now shares the pass with others, so its own rate drops.

  2. How much memory do a 20-billion-parameter model's weights take at 16 and at 4 bits, and what uses the rest?

    Answer

    About 40 GB and about 10 GB. The rest holds the KV cache for concurrent sequences, plus activations and runtime overhead.

  3. When is self-hosting cheaper than a managed API?

    Answer

    Only when the GPU is kept busy: an idle GPU is still paid for. For the reference service, break-even against a small managed model was about two million questions a month. Data residency or sustained high load can justify it for other reasons.

  4. What does a gateway add once several services call models?

    Answer

    Shared authentication and keys, request and token limits per tenant, routing to the cheapest suitable model, fallback on errors or rate limits, and central logging and cost tracking.
