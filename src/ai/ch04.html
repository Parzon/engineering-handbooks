Retrieval-augmented generation

Retrieval-augmented generation is a pipeline of a dozen stages that each fail differently: debug it backwards from the answer, measure retrieval apart from generation, and enforce who may see what inside the retrieval query itself.

At a glance
  • "Use a vector database" names one stage out of twelve. Most failures are in chunking, filtering, fusion and context, not the index.
  • The chunk is both the unit you find and the unit the model reads; split at document structure by default.
  • Hybrid search: keywords find exact identifiers, embeddings find paraphrases, rank fusion merges them without calibrating scores.
  • A tenant filter applied after an approximate index can return nothing, silently. Filter in a form the planner can use first.
  • Measure retrieval with recall@k and MRR on labeled questions; a chunk never retrieved cannot be used, whatever the prompt says.

The pipeline, and how to debug it

Chunking

Embeddings, similarity and indexes

An embedding model maps a text to a vector so that similar meanings point in similar directions. Query and document are embedded separately, so documents are embedded once, ahead of time. Three facts cause most embedding bugs. Asymmetric models want task prefixes (search_query: , search_document: ), which are part of the model. Vectors from different models, dimensions or prefixes are incomparable, and nothing errors: similarity search keeps returning rows, now meaningless, so the reference service stores an embedding key with every vector and searches only today's. And a vector is as sensitive as its text: research has recovered much of the original text from embeddings.

On vectors normalized to length one, cosine, dot product and Euclidean distance rank identically; cosine is the safe default when normalization is not guaranteed. Exact search compares every row and is fine up to many thousands. Approximate indexes trade recall for speed by design: HNSW is a layered graph, fast and memory-hungry, with build-time parameters (m, ef_construction) and a query-time candidate width (ef_search, 40 by default in pgvector); IVFFlat clusters the vectors and needs data to train on. In Postgres, HNSW comes from the pgvector extension, the operator class must match the query's operator, and the query must be shaped ORDER BY embedding <=> $q LIMIT n, or Postgres quietly scans every row.

Hybrid search and fusion

Retrieval that respects who is asking

In the repoapps/api/app/runbooks.pythe team filter and the two retrievers

The SQL fragments that hybrid search is assembled from, with the measurement that decided the filter's form in the comment.

  • The team filter is a plain team_id = ANY(...), never hidden behind an OR, so the planner can read the team's rows by their index.
  • Each retriever returns its best :candidates; ranks are numbered outside the inner query, so the vector index serves the ORDER BY distance LIMIT.
  • Only vectors with today's embedding key are searched: vectors from another model or prefix would be meaningless.
# The team filter comes in two forms, not one "(:team_ids IS NULL OR ...)":
# measured on 50,000 sections in 100 teams, a one-team caller's semantic
# search behind that OR (and row-level security's own) got the HNSW index:
# 0 results without iterative scans (all 40 candidates were other teams'),
# 20 in 32-71 ms with them. The plain "team_id = ANY(...)" lets the planner
# read the team's rows by its index and sort them exactly: 20 in 0.8-1.6 ms
# (three runs of make bench-rag-filter).
_ALL_TEAMS = "TRUE"
_SOME_TEAMS = "c.team_id = ANY(CAST(:team_ids AS bigint[]))"
_KEYWORD = """
keyword AS (
    SELECT id, row_number() OVER (ORDER BY rank DESC, id) AS rank_no
    FROM (
        SELECT c.id, ts_rank_cd(c.search, q.query) AS rank
        FROM runbook_chunks c, (SELECT {terms} AS query) q
        WHERE c.search @@ q.query AND {teams}
        ORDER BY rank DESC, c.id
        LIMIT :candidates
    ) k
)"""
# The inner ORDER BY distance ... LIMIT is what the HNSW index serves; the
# ranks are numbered outside it, so no window sorts the whole table.
_SEMANTIC = """
semantic AS (
    SELECT id, distance, row_number() OVER (ORDER BY distance, id) AS rank_no
    FROM (
        SELECT c.id, c.embedding <=> CAST(CAST(:embedding AS text) AS vector) AS distance
        FROM runbook_chunks c
        WHERE c.embedding_key = :embedding_key AND {teams}
        ORDER BY c.embedding <=> CAST(CAST(:embedding AS text) AS vector)
        LIMIT :candidates
    ) s
)"""

Measuring retrieval

Context, citations and freshness

  • Too few chunks, and the model invents. Given one of the four sections it needed, it wrote a step the runbook never had, without its safety conditions, and cited it with full authority. The reference service now puts four sections in context.
  • Too many, and cost, latency and dilution grow; models use the start and end of a long context best, so the best chunks go first, deduplicated.
  • Citations are numbered and verified. A number outside the list is an invented citation, counted as a hallucination signal. Parse tolerantly: asked for [R1], the model also wrote (R1), 【R1】 and a bare R1. A valid citation proves a chunk was referenced, not that it supports the claim; that needs a judge.
  • Freshness and deletion. Show each chunk's date; ingest idempotently by document identity and content hash, re-embedding only what changed; and make deletion reach the chunks, or deleted text keeps being retrieved.
  • No distance cutoff by default. With one model, relevant sections reached distance 0.43 while unanswerable questions began at 0.41. A cutoff is per model, and only after measuring; otherwise the prompt and evals handle irrelevant chunks.

Documents are untrusted input too: an instruction planted in a document is indirect prompt injection, and anyone who can edit a document can attempt it. The same architectural bounds apply as for any injected text, and secrets in documents reach the embedding provider on every save, so redaction must come before any model call, not only before the chat prompt (Chapter 9).

Questions

  1. An answer is wrong. In what order do you examine the pipeline, and why?

    Answer

    Backwards from the answer: the check, generation, the prompt, the context, fusion, each retriever, chunking, parsing, ingestion. Stop at the first stage that is wrong; everything after it only looks wrong.

  2. Why combine keyword and semantic search, and how are their results merged?

    Answer

    Keywords find exact rare tokens such as error codes; embeddings find paraphrases. Reciprocal rank fusion merges them by rank alone, so their scores need no calibration; a reranker fixes its equal weighting.

  3. What is the overfiltering trap, and how is it avoided?

    Answer

    An approximate index returns its nearest candidates and the tenant filter runs after; for a small tenant all candidates may belong to others, so nothing is returned. Use a filter the planner can apply first, iterative scans, or per-tenant indexes or partitions.

  4. What do recall@k and MRR measure, and what can a 19-question benchmark not tell you?

    Answer

    Recall@k: whether a relevant chunk is in the top k. MRR: how high the first relevant chunk ranks on average. A small benchmark shows each model works; it cannot rank models whose difference is a couple of questions.
