Part III · Building with models

Agents, tools and MCP

An agent lets the model choose its own steps and tools; that flexibility costs tokens, latency and predictability, so use the simplest architecture that solves the problem, and give any tool only the rights of the person asking.

At a glance
  • A workflow runs models and tools through code paths written in advance; an agent directs its own process.
  • Climb the ladder (one call, retrieval, a workflow, one agent, several agents) only when a measurement shows the lower rung falls short.
  • Measured in the reference service: the agent matched the fixed pipeline only once its prompt told it to do what the pipeline does, at 3.8× the prompt tokens.
  • Tools act as the asking user, take identity from the session, are read-only unless a person approves, and are validated, bounded and audited.
  • MCP is one protocol between AI applications and tools; a tool's description, and its output, are untrusted text that reaches the model.

The bounded loop, and the rules every tool follows, written at the top of the tools module.

  • The last round offers no tools, so the model must answer with what it has.
  • A repeated call is answered with a refusal the model can read, rather than run again.
  • No tool argument names a team or a user: identity comes from the session, so no text in the model's context can widen what a call reads.
  • Every call is validated, time-limited, audited and traced; what it returns is untrusted text, with credentials redacted.
async def _loop(llm: LLMClient, question: str, ctx: tools.ToolContext, emit: Emit) -> int:
    messages: list[Message] = [
        {"role": "system", "content": AGENT_PROMPT},
        {"role": "user", "content": redact(question)[0]},
    ]
    called: set[str] = set()
    max_steps = ctx.settings.agent_max_steps
    for step in range(max_steps + 1):
        # The last round offers no tools: the model must answer with what it has.
        offered = OPENAI_TOOLS if step < max_steps else None
        calls: list[ToolCall] = []
        text: list[str] = []
        async for item in llm.stream(messages, AGENT_PROMPT_REF, tools=offered):
            if isinstance(item, ToolCall):
                calls.append(item)
                continue
            if isinstance(item, str):
                text.append(item)
            await emit(item)
        if not calls or offered is None:
            return step
        messages.append(
            {
                "role": "assistant",
                "content": "".join(text),
                "tool_calls": [c.as_message_part() for c in calls],
            }
        )
        for call in calls:
            key = f"{call.name}:{_canonical(call.arguments)}"
            if key in called:
                result = tools.Result(
                    "You already called this tool with these arguments: use that result.",
                    False,
                    "repeated call refused",
                )
            else:
                called.add(key)
                result = await tools.call(call.name, call.arguments, ctx)
            await emit(ToolEvent(tools.label(call.name), result.ok, result.summary))
            messages.append({"role": "tool", "tool_call_id": call.id, "content": result.text})
    return max_steps

Tools, and the confused deputy

MCP: the Model Context Protocol

MCP's security model rests on the server, not on hints. Tool annotations such as "read-only" are hints and must not be trusted; servers validate, authorize and rate-limit; tokens are never passed through to downstream services; and hosts confirm sensitive calls. Tool poisoning is a malicious server whose tool descriptions, or its server instructions, reach the model as prompt text: install MCP servers the way you install dependencies. A large public server illustrates the trade-offs: a handful of tools, one of which runs model-written code in a sandbox that can reach any API of the platform. The short tool list keeps the prompt cheap and the choice easy, but the power then sits in one tool, so the credentials behind it, not its "destructive" hint, set the blast radius. Its results include a record of what actually ran, and its description tells the model to check that record before trusting the return value.

Skills are a related idea: a folder with a markdown file whose short description sits in the model's context and whose full text loads only when a task matches, often with scripts the agent runs and reference files it reads. A skill teaches how to do a job; a tool does it. Both are instruction channels from a source you must trust, and a skill's scripts are code that runs with the agent's permissions: vet and pin them like any dependency.

Memory, approval gates and the Rule of Two

  • Short-term memory is the message list for one task. Keep tool results small (counts, ids, a bounded number of items) and trim or summarize old ones.
  • Long-term memory is an external store read back through retrieval, scoped per user and tenant. A planted instruction that gets saved steers every later session: treat a memory write like a tool write.
  • Several agents (a supervisor with workers, or handoffs between specialists) pay for broad, parallel tasks and huge contexts. They cost tokens (one provider measured agents at about 4× a chat's tokens and its multi-agent system at about 15×), coordination failures and harder evaluation.

Observing and evaluating an agent

A trace per answer holds an agent span, a model span per call and a tool span per tool call; metrics count steps per answer (a bump at the limit means looping) and tool calls by tool and outcome. Evaluate the outcome end to end on the same cases as the non-agent version, and the trajectory: model calls, tool calls, which tools, errors and steps that hit the limit. A right answer reached through six calls is a cost problem that answer-only evals miss. In the reference service, the audit trail of each tool call is what showed the agent filtering too hard.

Where an agent runs: your code, n8n, or a managed platform

Once the ladder says a workflow or an agent, there are three places to build it: in your own code, as the reference service does; in a workflow tool such as n8n; or on a managed agent platform such as AWS's AgentCore. They differ in who owns the loop, who runs the servers, and who provides the controls this chapter asks for. Choosing among them is an AI design decision; running whichever you choose is cloud work, covered in Handbook 3.

n8n: a workflow of nodes

n8n is a workflow automation tool with a visual editor, available as n8n Cloud or self-hosted. A workflow is a set of connected nodes. A trigger node starts it: a schedule, a webhook, an event in an app, a chat message. Every other node acts: it calls an app, transforms data, branches, or waits. Data passes between nodes as an array of items, each an object under a json key (and binary for files), and most nodes run once per item. Each node carries settings that decide failure behavior: Retry On Fail, and On Error to stop the workflow, continue, or continue through an error output that a later node can handle. A workflow can call another as a sub-workflow, and an error workflow runs when a workflow fails. Credentials for apps are stored in n8n and chosen on the nodes that use them; by default a workflow uses the same credential whoever runs it, and n8n also offers end-user credentials, where each user's own is used.

Where no node fits, the Code node runs JavaScript, or Python through task runners (the older Pyodide-based Python was removed in n8n 2.0). On n8n Cloud, Python code cannot import libraries; self-hosted, modules must be installed in the runner image and allowed explicitly. n8n's documentation calls task runners the only isolation layer between user code and n8n, and recommends running them in external mode, as separate containers. Community nodes, published by others, have full access to the machine n8n runs on and to the data in its workflows. n8n inspects some and lists them as verified; unverified ones come straight from npm, are not available on n8n Cloud, and can be switched off on a self-hosted instance.

To scale a self-hosted instance, n8n's queue mode splits the work: the main instance takes timers and webhook calls and creates executions without running them; Redis queues them; workers pick them up and run them; Postgres stores the data. Queue mode is not supported on SQLite, the default database, and every worker needs the main instance's encryption key. Finished executions are pruned by default after 14 days or past 10,000. Features such as SSO, Git-based version control, multiple environments and log streaming need a paid plan.

n8n's code is published under the Sustainable Use License, not an open-source license. It allows use for your own internal business purposes, building workflows for clients as a service, and running n8n behind your own product. It does not allow hosting n8n as a service where clients build workflows, or letting external users build or configure workflows through your product. Read the license before a product depends on it.

AWS: AgentCore, and what happened to Bedrock Agents

AWS's first managed agent service, Bedrock Agents, is now Bedrock Agents Classic: closed to new customers, in maintenance mode, with no new features and a frozen model list. Accounts that already use it keep it, and AWS recommends migrating to Amazon Bedrock AgentCore. Bedrock itself, its models, knowledge bases and guardrails, is unaffected. AgentCore is a set of services that work together or alone, with any framework and any model. AWS offers two ways to run an agent on it, and its advice is plain: use the harness unless you have a specific reason to own the loop yourself.

Limits shape the design. A synchronous request may run 15 minutes, a streaming connection 60, and an asynchronous job 8 hours; payloads go up to 100 MB. In an AWS account, AgentCore runs your agent under an execution role it assumes, which grants pulling the image from ECR and writing logs, traces and metrics. AWS warns that its managed full-access policy is broad and that the policies its CLI creates are for development only, so production roles are written by hand. The harness has no charge of its own; you pay for the underlying capabilities as you use them.

Questions

  1. Why would a team build an automation in n8n rather than in Python, and when should it move to code?

    Answer

    n8n changes who can build and change the automation, and how fast: people who own a process wire apps together in a visual editor, with ready-made integrations, per-node retries and an execution log. It moves to code when it becomes part of the product, must pass evaluations before each release, needs a loop or permissions the tool cannot express, or would let external users build workflows, which n8n's license does not allow.

  2. On AgentCore, when would you choose Runtime over the harness?

    Answer

    AWS's advice is the harness unless you have a reason to own the loop. Reasons are an existing agent codebase in a framework, or patterns the harness cannot express: a framework of your choice, graph or workflow-style orchestration, two-way streaming. Runtime runs your container in the same isolated per-session microVMs, and you call Memory, Gateway and Identity from your code.

  3. When should you not use an agent?

    Answer

    When the steps are known in advance, when latency or cost matters, when the result must be predictable and auditable, and when the model is small. Code the steps as a workflow instead.

  4. What guards does an agent loop need?

    Answer

    A step limit with a final call that offers no tools, refusal of repeated identical calls, timeouts per tool and per answer, optionally a token budget, and tool errors returned as readable results rather than crashes.

  5. What is the confused deputy problem for tools, and how is it avoided?

    Answer

    A tool with more rights than the user lets whoever steers the model use those rights. Tools act as the asking user, with tenancy from the session and no arguments naming a team or user.

  6. What are MCP's two kinds of error?

    Answer

    A protocol error, such as an unknown tool, is a JSON-RPC error. A tool that ran and failed returns a normal result marked isError, which the model can read and correct.
