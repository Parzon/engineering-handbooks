Part IV · Proving it works

Evaluation

Evaluation turns "the answers look better" into a measurement a reviewer can trust: versioned cases, checks that are themselves checked, enough repeats to see rare failures, and a statistical comparison with a baseline.

At a glance
  • There is no single "accuracy" for generated text; a system is measured on several metrics, each tied to a requirement, and a change is judged on all of them at once.
  • Cases in Git, in kinds: quality cases (grounding, refusal) gated on a pass rate; safety cases (injection, isolation) that must pass every run.
  • Deterministic checks first; a judge model for what no substring can decide, calibrated against human labels before it is trusted.
  • Zero failures in n runs bounds the failure rate below about 3/n. To see a failure of rate p, run about 3/p times.
  • A regression is a case that fails significantly more often than in the baseline, not one that failed once.

No single accuracy

Accuracy needs one right answer per input. Generated text can be wrong as a false fact, a fact the sources do not support, a refusal where it should answer, an answer where it should refuse, a leak, or a right answer that took six model calls. So each requirement gets its own measurement, and every change is judged on all of them.

Cases, checks and the gate

One case, and the test that decides whether a change made it worse.

  • The case's notes record what it caught and why it is worded as it is, so the next person does not "simplify" it back into a blind check.
  • Its deterministic checks catch the answer that leaked before; the judge decides the behavior no substring can.
  • The regression test asks how likely the new failures would be if nothing had changed; "passed before, fails now" had turned noise into regressions a third of the time.

# A regression is a case that fails significantly more often than in the
# baseline, not one that failed once. Measured: a case failing 1 run in 30
# fails a 10-run check a third of the time - "passed before, fails now"
# turned sampling noise into regressions.
REGRESSION_P = 0.05


def fisher_worse(fails_now: int, runs_now: int, fails_before: int, runs_before: int) -> float:
    """One-sided Fisher exact test: the chance of at least `fails_now`
    failures among the current runs if both sets of runs shared one failure
    rate. Small = the current runs are really worse."""
    total_runs, total_fails = runs_now + runs_before, fails_now + fails_before
    denominator = math.comb(total_runs, runs_now)
    return (
        sum(
            math.comb(total_fails, x) * math.comb(total_runs - total_fails, runs_now - x)
            for x in range(fails_now, min(total_fails, runs_now) + 1)
        )
        / denominator
    )

Read the answers before trusting a number

The first runs of the reference harness found four wrong checks and one model failure: a correct answer written with a non-breaking hyphen failed a substring check (so every text check now normalizes typography and case first); a phrase list missed "I'm not seeing any alerts"; and a judge rubric asked for the wrong thing, twice. Worse than a missing check is one that passes wrong answers: the off-topic case once checked only that the answer did not say "Paris", and a later prompt answered "There are no alerts." with an alert in the list, in 8 runs of 40, all of them green.

How many runs: the statistics that matter

  • The rule of three. Zero failures in n runs means the failure rate is below about 3/n, with 95% confidence. "Never" is not a claim: 0 leaks in 200 runs means "below 1.5%".
  • Small samples hide rare failures. In the reference project, 110 passing calls missed a behavior that later showed up 8 times in 40 runs, and a prompt leak that happened 5 times in 200.
  • The target is the bound, not the number of runs. One leak in 200 runs puts the bound at 2.35%, over a 1.5% target; 400 more runs with one more leak brought it to 1.05%. Each failure seen raises the runs needed.
  • Is a difference real? Fisher's exact test: 5 leaks in 200 against 0 in 200 would happen with probability 0.03 if both prompts leaked equally, so the difference is real; 1 against 0 means nothing. In the gate, 0 to 1 failures in 10 runs is noise (p = 0.5), and 0 to 5 is a regression (p = 0.016).

The judge

A judge is a second model asked a yes-or-no question about an answer: whether an answer that quotes a malicious command warns against it or recommends it, or whether "I don't have that information" declines correctly. It is a model, so it can be wrong. The reference rules: calibrate it against answers a person labeled YES and NO, including hard ones (a correct answer in odd words, a bad answer that looks fine), with at least one NO per criterion, or a judge that always says YES looks perfect; use a model from another family than the one under test, at temperature 0; ask for a short reason, then the verdict; and fail the run when a verdict is missing.

Datasets, offline and online

"How do we know this change made it better?"

  1. Metrics on a dataset: the versioned suite, representative of real traffic.
  2. Before and after under the same conditions: the same cases, judge and settings, with enough repeats.
  3. Beyond the noise: a significance test on the pass rates, not "three more cases passed once".
  4. Nothing else got worse: safety, refusals, latency and cost per request held.
  5. Production agrees: online signals after release, because no offline set is all of reality.
How to say it

"Every prompt or model change runs the eval suite against a committed baseline: safety cases must pass every run, quality cases are gated on a pass rate, and a regression is a Fisher test, not one failure."

"Zero failures in two hundred runs means below one and a half percent, not never. We size runs from the failure rate we need to rule out."

Questions

  1. A case failed 1 run in 10; after a prompt change it passes 10 of 10. Is it fixed?

    Answer

    Not shown. 1 against 0 in 10 runs is well within noise; 0 failures in 10 runs only bounds the rate below about 30%. You need many more runs (about 3/p for the rate you want to rule out) and a significance test against the earlier runs.

  2. Why must a safety case have a deterministic check, not only a judge?

    Answer

    The judge is a model reading output from a model that may have been injected; it can be wrong or manipulated. A deterministic check is a floor that cannot be talked out of its verdict.

  3. What does calibrating a judge prove, and what does it not?

    Answer

    It proves the judge agrees with human labels on the labeled answers, including a NO for each criterion, so it is not simply approving everything. It does not prove it is right on answers unlike those, or that it cannot be injected.

  4. What five things make a convincing answer to "how do we know this change made it better?"

    Answer

    Metrics on a representative dataset; before and after under the same conditions; a difference beyond noise; guardrail metrics that held; and production signals that agree.
