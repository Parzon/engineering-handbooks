Part IV · Proving it works

AI observability

AI quality is per answer, so the trace of one request is the unit of diagnosis: it records what the model was given, how it was asked and what came back, while keeping the content itself out of the telemetry by default.

At a glance
  • Trace the chain: request, retrieval (embed, search), prompt, model call, tool calls, response; one span per step, one trace per request.
  • OpenTelemetry's GenAI conventions name the spans and attributes: models, tokens, finish reasons, time to first chunk, prompt version.
  • Record enough to explain an answer later without storing it: ids, counts, ranks, hashes, versions.
  • The dangerous failures are silent: the request succeeds, the answer reads well, and only the trace shows the missing section.
  • Telemetry is a copy of the data. Content is opt-in, and a trace store ignores tenancy.

One question, one trace

Diagnosing a worse answer

Compare the bad answer's trace with a good one for the same question, in three steps: what was the model given (documents, sections, prompt version); how was it asked (model, output limit, reasoning level); and what came back (finish reason, tokens, outcome). The reference project broke four settings, one at a time, and diagnosed each from telemetry alone.

Linking the signals

  • Versions as a metric. An info metric carries the release, the prompt (name and version), the model and the embedding model. When answers change, line the change up with this first.
  • Trace ids everywhere. In every log line, in the stream's first event, and in eval reports: from a failing eval answer to what it was given is one click.
  • Evals as traces. Each case run is a trace, each check an evaluation event on it, and the service's spans sit under the case. In the reference project, one failing case's trace showed both the check ("the 'Free space' section was never cited") and the cause (retrieval gave one section).
  • Audit trail beside it. A trace is a sample, for finding where time went; the record of who did what, for every request, is the audit trail (Chapter 9).
How to say it

"Each answer has a trace with what it was given, by id and rank, the prompt version and hash, the model that answered, tokens and finish reason. No content by default: a trace store ignores tenancy."

Questions

  1. An answer got worse with no errors anywhere. How do you find out why?

    Answer

    Compare its trace with a good one for the same question: what it was given (documents and their ranks, section count, prompt version), how it was asked (model, output limit, reasoning level) and what came back (finish reason, tokens, outcome). Stop at the first difference.

  2. Why does "time to first token" need to be split in two?

    Answer

    Time to the first chunk measures the provider starting (queueing, loading the model); from the first chunk to the first answer token measures a reasoning model thinking. One number cannot tell a cold model from a thoughtful one.

  3. Why is content kept out of traces by default?

    Answer

    A trace store ignores tenancy, keeps data on its own retention (often at a vendor) and escapes deletion requests; and redaction removes secret formats, not sensitive facts.

  4. What is the difference between head and tail sampling?

    Answer

    Head sampling decides at the start of a trace, so it keeps failures at the same rate as everything else. Tail sampling decides at the end, in a collector holding whole traces, so it can keep every error and slow trace plus a share of the rest.
