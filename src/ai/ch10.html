Cost and performance

A model's bill is requests × tokens per request × price per token; knowing which factor moved explains every cost jump, and each lever that lowers it has a quality cost that only evals can measure.

At a glance
  • Output costs five to eight times more per token than input, and hidden reasoning is output; yet in retrieval-heavy services the prompt is usually most of the bill.
  • Context size is the first lever; a cheaper model is the biggest one; both need evals before and after.
  • Provider prompt caching needs a long, stable prefix; semantic caching of answers is wrong when answers depend on live data or on who asks.
  • Self-hosting is cheaper per token only when the GPU stays busy.
  • Alert on each factor separately: a jump in tokens per request is invisible to an alert on request volume.

The cost model

The levers

Prompt caching charges about a tenth for input the provider has seen recently, if it is a long, identical prefix, with static content first. Some providers also charge extra to write the cache (on Anthropic's models, 1.25 times the input price for a five-minute cache), so it pays only when the prefix is read again before it expires. The minimum prefix depends on the model, from 512 to 4,096 tokens: check the one you use. It pays for a large system prompt, a document asked about many times, or a long conversation; it does not pay when the stable part is short and variable context sits early. Semantic caching reuses an answer for a similar question. In the reference benchmark, the closest pair of questions (distance 0.261) was a question and its follow-up, which needed the next step; and since answers are built from the asker's teams' live alerts, a cached answer is either stale or another team's. A cache key including the access scope and the context's version leaves almost nothing to hit.

Performance, briefly

The latency levers follow from how models run (Chapter 2): a shorter prompt shortens the time to first token; streaming makes the user wait for the first token rather than the whole answer; an output cap bounds the worst case; and reasoning effort trades quality for tokens and seconds. In the reference service, adding four runbook sections raised the median time to first token from 0.21 to 0.28 seconds, retrieval included, and hybrid search alone took about 10 milliseconds. For a self-hosted model, batching halved the cost per output token ($2.93 to $1.41 per million) and halved each stream's speed. Capacity with a hosted provider is planned from its tokens-per-minute quota, which binds long before the service's own CPUs (Handbook 2, Chapter 16).

Questions

  1. Output tokens cost more than input tokens. Why can the prompt still be most of the bill?

    Answer

    Because there are many more of them: in the reference service about 1,300 prompt tokens against about 170 answer tokens, so eight times the tokens outweigh five times the price.

  2. The bill doubled overnight. How do you find out why?

    Answer

    Split cost into requests, tokens per request (prompt and completion apart) and price per token; find which moved; look at what changed in it (deploys, settings, the versions metric); then revert, cap the damage, and only then optimize with evals.

  3. When does provider prompt caching help, and when does a semantic answer cache hurt?

    Answer

    Prompt caching helps when a long, identical prefix is reused often. A semantic answer cache hurts when answers depend on live data or on who asks: a similar question can need a different answer, and a cached one can be stale or another user's.
