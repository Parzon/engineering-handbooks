Part VII · The data platform

Warehouses, lakehouses and streams

The modern data platform keeps the ideas of the classic warehouse (staging, cleansing, star schemas) but separates storage from compute, loads raw data before transforming it, and stores tables in open formats that several engines can read.

Data and cloud, not AI. This chapter is about the data platform: warehouses such as Snowflake, lakehouse tables and streams, all run on a cloud. A team needs it whether or not it uses models. Chapter 14 is where data meets AI. A data platform's own AI features, such as Snowflake Cortex, are AI features: judge them with Chapters 4 to 8.

At a glance
  • Each tool lives in one layer: storage, file format, table format, catalog, compute, or movement. Knowing the layer explains the tool.
  • Parquet lays bytes out by column; Iceberg turns a folder of Parquet files into a table with atomic commits, schema evolution and time travel.
  • Change data capture reads a database's write-ahead log and publishes every change as an event, with little query load on the source. It is not free: the source keeps its log until the consumer confirms it, so a stopped connector can fill the source's disk.
  • Bronze, silver and gold are the new names for staging, the conformed layer and the star schema.
  • Start with a warehouse and dbt; add a streaming log, a lakehouse table format or a dataflow tool only for a specific pain.
  • Snowflake separates cloud services, compute and storage: warehouses bill per second while running, and micro-partition metadata lets a query skip most of a table. It is a data platform; its AI features are a layer on top.

The layers

Change data capture and streams

The classic warehouse, renamed

Schema on write (Postgres) defines columns first and validates data as it loads. Schema on read (a semi-structured column holding JSON, queried by path) loads raw data and applies structure at query time: flexible and fast to ingest, with no enforcement and looser queries. dbt is the transformation layer: each model is a SELECT in Git, compiled into tables or views inside the warehouse in dependency order, with tests and documentation; it neither moves data nor schedules itself.

Snowflake, from the inside

Snowflake is the warehouse many teams meet first, so it pays to know how it works underneath. It is a managed service and nothing else: an account runs on AWS, Azure or Google Cloud, all three of its layers on that one cloud, and it cannot be installed on your own servers. It is a data platform, not an AI product. Its AI features sit on top of it, and this section keeps them to one paragraph at the end.

What makes a query cheap, and what you pay for

Every table is split automatically into micro-partitions in the order rows arrive, and Snowflake keeps each column's range of values per micro-partition. A query prunes in two steps: first the micro-partitions whose ranges cannot match its filter, then the columns it does not need. A filter written as a subquery does not prune, even when it returns a constant. Two caches help again: the result cache returns a repeated query's result without running it, for 24 hours (extended on each reuse, up to 31 days) as long as the query text is identical and the data has not changed; and each running warehouse caches the data it read, a cache that is dropped when the warehouse suspends, so the first queries after a resume can be slower.

The bill has three parts. Compute is paid in credits: warehouses per second while running, with a 60-second minimum each time one starts, doubling with each size step; serverless features such as Snowpipe; and the cloud services layer, charged only for the part above 10% of the day's warehouse use. Storage is billed monthly on the average bytes stored each day, and a longer Time Travel retention stores more. Data transfer is free into Snowflake and charged out of a region or cloud. Auto-suspend and auto-resume are on by default; the trade-off is the cache, so a dashboard warehouse that suspends after a minute saves credits and pays for it with slower first queries. A bigger warehouse makes one big query faster; more clusters of the same size (multi-cluster, an Enterprise feature) serve more users at once. Newer warehouse generations and types exist, and which is the default varies, so check what an account actually runs before comparing numbers.

Getting data in, and keeping tables current

Snowpipe Streaming has two architectures. The current, high-performance one offers named channels with ordered, exactly-once ingestion; the classic one is planned for deprecation, so new work should not start on it.

Open tables, access and the connection to AWS

  • Iceberg tables. Snowflake can keep a table in the open Iceberg format. Snowflake-managed, it gets full support, compaction and Fail-safe; on your own bucket you own its protection and recovery; and with an external catalog (such as AWS Glue) Snowflake's support is limited and it manages none of the table's lifecycle.
  • Access. Privileges go to roles, roles to users or to other roles, and anything not granted is denied. Each object is owned by one role. Keep ACCOUNTADMIN to a few people and hang custom roles under SYSADMIN. Network policies, written with network rules, decide who may connect at all; by default anyone may.
  • Reading your S3 without keys. A storage integration lets Snowflake assume an IAM role in your account, trusted only for Snowflake's IAM user and an external ID, and limited to the buckets you allow; no access keys are stored in Snowflake. It is the same keyless trust as a CI pipeline's (Handbook 3, Chapter 5). Snowpipe learns of new files from S3 event notifications delivered through SQS.
  • Private connectivity. AWS PrivateLink keeps traffic from your VPC to Snowflake off the internet, and needs the Business Critical edition or higher. It covers inbound traffic only, and Snowpipe's SQS notifications do not travel through it.

Its AI layer, kept apart

Snowflake Cortex is a set of AI features over the data: SQL functions such as AI_COMPLETE, AI_CLASSIFY and AI_EXTRACT, hybrid search for retrieval, and agents and text-to-SQL over semantic models. The models run inside Snowflake's security perimeter, and Cortex is billed differently from warehouses. These are AI features that happen to live in the warehouse; how retrieval, agents and evaluation work, and how to judge them, is in Chapters 4, 6 and 7.

Questions

  1. In Snowflake, when does a bigger warehouse help, and when do more clusters help?

    Answer

    A bigger warehouse gives one query more compute, so large queries finish faster (loading does not always speed up). More clusters of the same size, a multi-cluster warehouse, serve more queries at once: Snowflake starts clusters as queries begin to queue. Size is for heavy queries; clusters are for many users.

  2. How does Snowflake read files in your S3 bucket without storing AWS access keys?

    Answer

    Through a storage integration: an IAM role in your account whose trust policy names Snowflake's IAM user and an external ID, with permissions on only the buckets you allow. Snowflake assumes the role when it needs the files. It is the same keyless pattern as a CI pipeline assuming a role through OIDC.

  3. What problem does a table format such as Iceberg solve?

    Answer

    A folder of Parquet files has no atomic commit, so readers can see partial writes and schema changes are painful. Iceberg's metadata layer and an atomic swap of the catalog's pointer give ACID commits, snapshots for time travel, and safe schema evolution.

  4. Why is change data capture usually better than a nightly extract by modified date?

    Answer

    It reads the database's log rather than querying tables, so it adds little query load, is near-real-time, captures deletes, and the events can be replayed. Its cost: the source keeps its log until the consumer confirms it, so a stopped connector must be noticed before the source's disk fills.

  5. Map staging, the conformed layer and the star schema to their lakehouse names.

    Answer

    Bronze (raw, kept), silver (cleaned, deduplicated, typed) and gold (the Kimball model of facts and dimensions).
