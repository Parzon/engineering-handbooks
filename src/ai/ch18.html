Part VIII · Architecture and leadership

Working with AI coding agents

A coding agent is a fast, capable newcomer that never gets tired and is sometimes confidently wrong; teams get the speed safely by giving it a written contract in the repository, a plan-implement-verify loop, small changes, and a human who reviews, merges and owns the result.

At a glance
  • The loop: plan, review the plan, implement, verify with tests, types and lint, and write down what was learned.
  • State the goal as an outcome with its constraints, not as a method.
  • An instructions file in the repository is the contract: commands, conventions and prohibitions. When an agent gets something wrong twice, the fix goes there.
  • Tests are the real gate: untested generated code is as unmergeable as untested human code, and a test must never be loosened to get green.
  • Small pull requests, one concern each; a human merges and owns what was merged.

The repository is the contract

In the repodocs/handbook/code-style.mdrules for working with coding agents

The reference repository's team rules for agents, kept beside its code-style rules.

  • An agent reports what it ran, with the output: a claim of "done" without commands is a hope.
  • A failing check is information, never something to delete or loosen.
  • A secret pasted into a conversation is burned and must be rotated; agents read the example environment file, never the real one.
  • Destructive commands, and anything against a shared environment, need a human.
### Working with AI coding agents

1. **`AGENTS.md` is the contract.** It gives commands, conventions and
   prohibitions, and agents such as Claude Code and Codex read it. When
   an agent gets something wrong twice, the fix belongs in `AGENTS.md`.
2. **An agent runs `make check` before saying it is done**, and reports
   what it ran, with the output.
3. **Review agent code like a capable newcomer's code:**
   - read the tests first;
   - check the failure paths and the timeouts;
   - check that nothing was weakened to make a test pass.
4. **Never let an agent delete or loosen a test, an eval case or a
   calibration label** to get green. A failing check is information.
5. **Small PRs, one concern each.** Agents produce plausible code fast.
   A large diff hides the one wrong line.
6. **No secrets in prompts or chats.** A key pasted into a conversation
   is burned: rotate it. Agents read `.env.example`, never `.env`.
7. **A human merges, and owns what was merged.** An agent's confidence
   is not verification. The commands and numbers in the PR are.
8. **Destructive commands need a human:** deleting volumes, force
   pushes, dropping data, anything against a shared environment.

Reviewing agent-written code

Workflow tools beside code

Low-code workflow tools such as n8n sit next to coding agents in many teams. A workflow there is a JSON document (nodes, connections, parameters), so it can live in Git and an agent can write it; the tool's own MCP server and published skills are better than hand-written JSON, where agents invent node types and parameters. Exports carry credential names, not secrets, but a request node imported from a command line can carry authorization headers, so scan before committing. Credential ids, webhook URLs and the active flag are what break between environments. Use the workflow tool for orchestration and glue (prebuilt integrations, credentials, triggers, retries, flows that non-engineers can read), and code for real logic (unit tests, type checks, reviewable diffs, complex branching). Check the license: several such tools are source-available rather than open source.

Questions

  1. Why should a prompt to a coding agent state an outcome rather than a method?

    Answer

    An outcome with constraints ("the health check survives a database restart") lets the agent find the right change and gives a test for success; a method ("add a try/except at line 40") encodes a guess and cannot be verified against the real goal.

  2. What failure patterns do you look for when reviewing agent-written code?

    Answer

    Invented APIs or parameters, silently swallowed exceptions, clever one-liners nobody can maintain, tests that assert something trivial, and checks weakened to make the change pass.

  3. An agent keeps making the same mistake. Where does the fix go?

    Answer

    In the repository's instructions file, which every session reads, so the correction is permanent and visible to people too.
