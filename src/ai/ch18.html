Part VIII · Architecture and leadership

Working with AI coding agents

A coding agent is a fast, capable newcomer that never gets tired and is sometimes confidently wrong; teams get the speed safely by giving it a written contract in the repository, a plan-implement-verify loop, small changes, and a human who reviews, merges and owns the result.

At a glance
  • The loop: plan, review the plan, implement, verify with tests, types and lint, and write down what was learned.
  • State the goal as an outcome with its constraints, not as a method.
  • An instructions file in the repository is the contract: commands, conventions and prohibitions. When an agent gets something wrong twice, the fix goes there.
  • Tests are the real gate: untested generated code is as unmergeable as untested human code, and a test must never be loosened to get green.
  • Small pull requests, one concern each; a human merges and owns what was merged.
  • Rules in the instructions file are advice; hooks and CI are the gates. A skill or plugin is measured on your own tasks before it is adopted, and its token cost is read before it is installed.
  • Two reviewers with different questions beat the same reviewer twice; a simplify pass needs the diff and the surrounding code, not repetition.

The loop

The repository is the contract

In the repodocs/handbook/code-style.mdrules for working with coding agents

The reference repository's team rules for agents, kept beside its code-style rules.

  • An agent reports what it ran, with the output: a claim of "done" without commands is a hope.
  • A failing check is information, never something to delete or loosen.
  • A secret pasted into a conversation is burned and must be rotated; agents read the example environment file, never the real one.
  • Destructive commands, and anything against a shared environment, need a human.
### Working with AI coding agents

1. **`AGENTS.md` is the contract.** It gives commands, conventions and
   prohibitions, and agents such as Claude Code and Codex read it. When
   an agent gets something wrong twice, the fix belongs in `AGENTS.md`.
2. **An agent runs `make check` before saying it is done**, and reports
   what it ran, with the output.
3. **Review agent code like a capable newcomer's code:**
   - read the tests first;
   - check the failure paths and the timeouts;
   - check that nothing was weakened to make a test pass.
4. **Never let an agent delete or loosen a test, an eval case or a
   calibration label** to get green. A failing check is information.
5. **Small PRs, one concern each.** Agents produce plausible code fast.
   A large diff hides the one wrong line.
6. **No secrets in prompts or chats.** A key pasted into a conversation
   is burned: rotate it. Agents read `.env.example`, never `.env`.
7. **A human merges, and owns what was merged.** An agent's confidence
   is not verification. The commands and numbers in the PR are.
8. **Destructive commands need a human:** deleting volumes, force
   pushes, dropping data, anything against a shared environment.

Reviewing agent-written code

How an agent is extended: skills, plugins, hooks, MCP

A coding agent is a model inside a harness that reads, edits and runs things under a permission policy. Everything you add to it lands in one of six places, and they differ in two ways that matter: whether the agent can ignore it, and what it costs on every turn. The instructions file is advice the model reads once per session. A skill is a markdown file of instructions loaded when its trigger matches or when it is invoked by name; only its one-line description is in context until then. A plugin bundles skills with hooks (shell commands the harness runs at events: session start, before and after a tool call, when the agent wants to stop), MCP servers (tools from outside: a browser, a documentation index, a design file) and subagents (a fresh context with a narrower job). A hook is the one extension the model cannot talk its way around: a blocking exit code stops the edit or the turn, and that holds even when permission prompts are switched off. The same harness runs headless, from a script, which is how it joins a pipeline and how you can measure it.

One extension deserves a security note. Some plugins build a map of the repository at session start and inject it as hidden context the user never sees. That is repository text reaching the model as instructions, which is the prompt-injection channel of chapter 9 opened from inside the toolchain: a file in a dependency or a pull request can carry text addressed to the agent. Prefer plugins that show what they inject, switch such maps off where a flag exists, pin versions, and treat a plugin marketplace like any other dependency source.

Measure a skill before adopting it

A skill's own benchmark was run by its maintainer, on tasks chosen by its maintainer, with rules tuned on those tasks. The number to trust is the one you measure on your work, and the harness makes that cheap: the same task text, a fresh worktree from the same commit for every run, the agent allowed to read and edit but not to run commands (so the measure is what it writes, not what it can debug into shape), and your own checks afterwards, the same ones CI runs. Two arms, a handful of runs each, then read the diffs rather than only the totals. The reference build's own version of this is in the agent A/B lab.

Two readings from the diffs. The lean rule wrote the same endpoint with four files instead of five and half the test lines, and its replies ended with what it had skipped ("I did not check the index on that pair of columns"), which is worth more than the tokens saved. And the one run per arm that implemented a redundant retry passed every check: a green pipeline does not know a feature was unnecessary. Only reading the surrounding code did, which is why the simplification pass below needs the diff and the files, not the diff alone.

Three reviewers, three questions

Reviewing is where extensions differ most, because each one asks a different question. Three reviews of the same twelve-file security commit, by the same model, read-only:

ReviewerFindingsWhat it alone foundCost
A plain prompt: "review this like the engineer who will be paged"14 in 1,200 words; its top finding was wrong (checked against the running system)an unauthenticated route that blocks the event loop; a public static mount nobody had reviewed24 cents
A lean-code review skill6, ranked, each with "if we skip it"; none wrong; one doubt labeled as uncheckedput the one must-fix first: a size cap that missed two upload routes24 cents
A structure-only review skill ("maintainability, abstractions, file growth")9, all structural; ignored behavior on purposethe ownership check was pasted into ten places and belonged in one helper; a dev-only route should not be mounted in production at all; a request field that invited the original bug should be deleted15 cents

All three found the same four real defects. The plain prompt found the most and was the only one to lead with a false alarm; the lean review was the one a busy person could act on in one read; the structural review was the only one that would have prevented the next incident, because it asked where the rule lives rather than whether it was applied. Use two reviewers with different questions, not the same one twice. The same holds for the "simplify" pass people run before a pull request: three passes of the same simplifier on the same diff changed a few test lines and then nothing, in both arms; one pass given the diff and the surrounding code found that the whole change was redundant. Repetition buys nothing; context does.

Design with an agent: ambition, then a check

Left alone, an agent builds the page it has seen most: a cream background, one word of the headline in color, identical rounded cards. A design skill raises the ambition. The official one tells the agent to ground the look in the subject, choose typefaces on purpose, spend boldness in one place, and avoid a named list of tells: the cream-and-terracotta palette, black with one acid accent, broadsheet hairlines, the card kit, all-caps eyebrow labels, a middle dot between metadata, an arrow after every link, an entrance animation on every section. What that loop needs installed, in order of value. A browser the agent can drive: the Chrome DevTools MCP server (screenshots, the accessibility tree, device emulation, performance traces) or Playwright's command-line tool with its skills, which its maintainers now recommend over the MCP server for token cost. A written design system per project, in a format with a linter, so "follow the tokens" is a check rather than a hope; the agent's first job on a new page is three deliberately different design plans with ASCII wireframes, from which a person picks one, and that choice becomes the file. The official documentation of whichever motion or 3D library you chose, given to the agent as a skill or an MCP server, because models carry stale copies of these APIs; the major animation libraries publish skills or an llms.txt for exactly this reason. A deterministic detector for the generic tells, if one exists for your stack, as a hook after each edit, after reading what the hook installs: one popular detector's hook downloads a binary and runs it outside the tool-approval flow, which is the supply-chain question of the cloud handbook's chapter 4 arriving through a design tool. And the interaction rules a polish review checks: a visible focus ring, reduced motion respected, animations on transform and opacity only, tabular figures in tables. Skip the lookup-table skills that map a product category to a palette and a typeface: they return the same answer for every product of that kind, which is the generic page by another route. For calibration, of three hundred recent award-winning sites, about half tag an animation library, a third WebGL and a quarter a 3D library, and one in five uses none of those; the one documented award-level build with a coding agent was directed by a designer throughout, with the agent covering the unfamiliar code. Nothing in this section produces that from one prompt.

No randomized or independently replicated study shows that any of the popular loop systems, the brainstorm-plan-implement bundles or the specification-first kits, improves delivered quality. What has evidence is narrower: verification the agent must pass, a short contract, a plan a person edits, review in a fresh context, small changes. Those are what the loop in Figure 18.1 is made of; the bundles are packaging.

What you own when the agent writes the code

The point of all this is a different division of labor, not a faster typist. The engineer's day moves to the problem: what is being asked, by whom, what "done" looks like, what must never happen, and which risk tier the change sits in. Each of those becomes an artifact the agent can work from: a problem statement written as an outcome with constraints and its acceptance check, a plan the engineer edits before any code, the risk tier that decides how strict the human review is. The agent owns the implementation, the tests, the first review pass and the documentation, inside gates it cannot loosen. The gates own correctness of the cheap kind: formatting, types, lint, the unit tests, the architecture contract, the secret scan, and the rule that the agent never holds a credential that can delete production.

Three habits make the day work. Write the problem statement before opening the agent, with the check that proves it done. Start a non-trivial task in plan mode and edit the plan; a change you can describe in one sentence does not need one. Keep an agent session to one task in one worktree, and start unattended chores with a measurable goal, a turn limit and an allowlist. The rest is the loop, the contract and the review standards above, which have not changed.

Workflow tools beside code

Low-code workflow tools such as n8n sit next to coding agents in many teams. A workflow there is a JSON document (nodes, connections, parameters), so it can live in Git and an agent can write it; the tool's own MCP server and published skills are better than hand-written JSON, where agents invent node types and parameters. Exports carry credential names, not secrets, but a request node imported from a command line can carry authorization headers, so scan before committing. Credential ids, webhook URLs and the active flag are what break between environments. Use the workflow tool for orchestration and glue (prebuilt integrations, credentials, triggers, retries, flows that non-engineers can read), and code for real logic (unit tests, type checks, reviewable diffs, complex branching). Check the license: several such tools are source-available rather than open source.

Questions

  1. Why should a prompt to a coding agent state an outcome rather than a method?

    Answer

    An outcome with constraints ("the health check survives a database restart") lets the agent find the right change and gives a test for success; a method ("add a try/except at line 40") encodes a guess and cannot be verified against the real goal.

  2. What failure patterns do you look for when reviewing agent-written code?

    Answer

    Invented APIs or parameters, silently swallowed exceptions, clever one-liners nobody can maintain, tests that assert something trivial, and checks weakened to make the change pass.

  3. An agent keeps making the same mistake. Where does the fix go?

    Answer

    In the repository's instructions file, which every session reads, so the correction is permanent and visible to people too.

  4. A rule says "never edit the lint configuration to make a check pass". Where does it belong, and why?

    Answer

    In a hook that denies edits to the configuration files, and in CI as a required check with owners on those files. The instructions file is advice the model weighs against the task; a hook's blocking exit code is not negotiable, and CI is the one layer the agent cannot edit around.

  5. A colleague recommends a plugin whose README reports half the code at a fifth of the cost. What do you do before rolling it out?

    Answer

    Read what it installs and its always-on token cost; look for hidden context it injects; then measure it on your own tasks with the same task text, a fresh worktree per run and your own checks afterwards. Expect a fraction of the headline, and read the diffs, because a green run can still contain an unnecessary feature.
