Part III · Identity

Identity without keys

People, pipelines and running services each prove who they are to a trusted identity provider and receive credentials that expire on their own, so there is no permanent key anywhere to leak.

At a glance
  • Three kinds of caller need cloud access: people, CI pipelines and workloads. Each now gets temporary credentials, by a different route.
  • People sign in once a day through single sign-on with MFA. Their sessions end by themselves.
  • Pipelines use OIDC federation: the CI platform signs a token that says which job is running, and the cloud exchanges it for credentials that last an hour.
  • Workloads use a role attached to the compute. The platform hands out and rotates the credentials.
  • The trust policy is the security boundary. It is an exact match on claims, so write it from the token you actually receive, not from an example.

Three callers, three routes

The old model gave every caller a long-lived secret: a password, an access key, an SSH key. Each one had to be stored somewhere, rotated by someone, and revoked when a person left. The modern model replaces all of them with the same pattern. A caller proves who it is to a system that already knows it, and receives credentials with a short, fixed lifetime.

The rest of this chapter takes each lane in turn. Pipelines get the most space, because that is where the change is newest and where the configuration is easiest to get subtly wrong.

People: single sign-on, and no standing access to production

An engineer signs in once a day through the company's identity provider (Okta, Microsoft Entra ID and others), with MFA. AWS IAM Identity Center maps the groups that provider asserts to roles in each account: development, staging, production. The command-line tools then fetch short-lived role credentials as needed. When the sign-in session ends, usually after a working day, everything stops working until the person signs in again. A stolen laptop's credentials die on their own.

Production adds one more rule: people do not deploy by hand. The pipeline deploys through its own role. People are read-only by default and get elevated access only on request, for a fixed time, and every use of it is recorded. This is often called break-glass or just-in-time access.

The reference build used a single throwaway account, so it signed in with the simpler aws login. The idea is the same: a browser sign-in that yields temporary credentials, and no access keys on disk. Root user access keys were never created.

Pipelines: OIDC federation

A CI job is the caller with the most power and the least supervision: it runs automatically, on shared infrastructure, and can push images or change infrastructure. It also cannot type a password. The old answer was an access key stored in the CI system's secrets. The modern answer is OpenID Connect (OIDC) federation: the CI platform vouches for the job, and the cloud decides whether to trust that.

Four pieces make it work:

  1. The job asks for a token. GitHub signs a JSON Web Token (JWT) for each job that has permissions: id-token: write. Without that line, no token is issued.
  2. The token describes the job. Its iss (issuer) is GitHub's token service. Its aud (audience) is whatever the job asks for: the AWS login action, aws-actions/configure-aws-credentials, asks for sts.amazonaws.com, while a token fetched without an audience carries the repository owner's URL and fails the trust policy. Its sub (subject) names the repository and either the git ref that triggered the job or the GitHub environment the job runs in.
  3. AWS trusts the issuer once per account. An IAM OIDC provider entry tells AWS to accept tokens signed by GitHub's published keys.
  4. A role decides which jobs it will serve. Its trust policy allows sts:AssumeRoleWithWebIdentity only when aud and sub match. A different repository, branch, tag or environment is refused.
In the repoinfra/aws/cicd.pythe OIDC provider and the image-push role

This CDK stack (Python that becomes CloudFormation) creates the account's one OIDC provider for GitHub and the role the release workflow uses to copy images into Amazon ECR.

  • SUB_PREFIX is the subject read from the repository's own OIDC setting, not typed from an example. The comment says how to read it.
  • The audience must be exactly sts.amazonaws.com.
  • The subject must be a version tag of this repository. A pull request, a branch push or a fork produces a different subject and gets nothing.
  • A version tag is only as trustworthy as the right to create one. A tag runs the release workflow of the commit it points at, so a tag on another branch could drop the workflow's "tag is on main" check. A tag ruleset lets only admins create, move or delete v* tags, and the comment says that this trust depends on it.
  • Sessions last at most one hour.
  • Push and pull are granted on the three image repositories only. ecr:GetAuthorizationToken cannot be scoped to a repository, so it is the one permission on *, and the code says why.
# This repo issues GitHub's "immutable subject" claim, which embeds the numeric owner and repo IDs
# (survives renames, blocks a re-created repo of the same name). Read it with:
#   gh api repos/Parzon/triage-assistant/actions/oidc/customization/sub
# A copy of this template has other ids: put its own prefix here (the same command, on its repo),
# or no role can be assumed. scripts/new-project.sh renames the repo, not these numbers.
SUB_PREFIX = "repo:Parzon@124113141/triage-assistant@1381921470"
ISSUER = "token.actions.githubusercontent.com"
# AWS trusts GitHub's signed tokens (one provider per account).
provider = iam.OpenIdConnectProvider(
    self, "GitHub", url=f"https://{ISSUER}", client_ids=["sts.amazonaws.com"]
)
role = iam.Role(
    self,
    "EcrPush",
    role_name="triage-gha-ecr-push",
    max_session_duration=Duration.hours(1),
    assumed_by=iam.WebIdentityPrincipal(
        provider.open_id_connect_provider_arn,
        conditions={
            "StringEquals": {f"{ISSUER}:aud": "sts.amazonaws.com"},
            # Only a release tag of this repo: not a PR, not a branch, not a fork. A tag
            # pushed on any branch runs that branch's release.yml, which could drop its
            # "tag is on main" check: the repository's tag ruleset, which lets only admins
            # create v* tags, is what makes this a release (using-this-template.md).
            "StringLike": {f"{ISSUER}:sub": f"{SUB_PREFIX}:ref:refs/tags/v*"},
        },
    ),
)
for repo in repos.values():
    repo.grant_pull_push(role)  # scoped to these repos, not ecr:*
# GetAuthorizationToken cannot be scoped to a repository.
role.add_to_policy(
    iam.PolicyStatement(actions=["ecr:GetAuthorizationToken"], resources=["*"])
)

One role per job, gated where the risk is

The reference build has two pipelines that touch AWS, and each has its own role. Copying images is low risk and happens on every release, so its role trusts any version tag. Deploying changes production, so its role trusts only jobs that run inside a GitHub environment named aws-demo.

That choice moves the approval rules out of the trust policy and into GitHub. When a job names an environment, its token's subject ends in :environment:aws-demo instead of the git ref. The environment's own protection rules then decide which jobs may run in it: here, only those from protected branches, and only after a required reviewer approves. That reviewer is what turns continuous deployment into deploy-on-approval, and adding or removing one never touches AWS.

In the repo.github/workflows/deploy.ymland the deploy role ininfra/aws/cicd.py

The deploy job names the environment and asks for a token. Then one action exchanges the token for credentials. The role ARN is a repository secret. It grants nothing on its own, but it names the AWS account, and GitHub masks only secrets in public logs: a variable is printed with every step's inputs. A job's if cannot read secrets, so a first job reads it and answers yes or no. While it is unset, nothing deploys, so a copy of the template works without an AWS account.

  • environment: name: aws-demo is what changes the token's subject.
  • id-token: write is granted to this job only, not to the whole workflow.
  • mask-aws-account-id hides the account id where the action and CDK print it.
  • The deploy role may assume only the roles that cdk bootstrap created. CloudFormation does the actual work with its own execution role.
  • Here the subject is matched with StringEquals, because there is no wildcard to allow.

Workloads: roles attached to the compute

A running service should never hold a key either. On AWS, a role is attached to the compute itself: a task role for an ECS task, an instance profile for an EC2 VM. The platform serves that role's credentials to the code at runtime and rotates them. Your code, using the standard AWS SDK, picks them up without any configuration.

ECS has two roles per task, and mixing them up is a common mistake. The task execution role is used by ECS itself, before your code runs, to pull the image and inject secrets. The task role is what your code may call once it is running, such as S3 or a queue. A service that needs no AWS API at runtime needs no task role at all.

Application secrets that are not AWS credentials, such as a database password or a model provider's API key, follow the same principle. They are generated by Secrets Manager, read by ECS when the task starts, and handed to the container as environment variables. They never appear in the image, the task definition, the CloudFormation template or the repository.

In the repoinfra/aws/service.pyandinfra/aws/vm.py

Two helpers in the ECS stack: one asks Secrets Manager to generate a secret, the other tells ECS to inject a field of it into a container at start. The VM stack's docstring lists what makes a single VM acceptable to a platform team.

  • Secrets are generated by AWS. Nobody types or sees them.
  • The comment on exclude_punctuation records a real constraint: the api builds a database URL from the password.
  • In this throwaway account a secret is deleted with the stack; the production: comment says to keep it (RETAIN), since the database it opens may outlive the stack.
  • The VM has no SSH key and no port 22. Images come from ECR through the instance role, so no registry password exists anywhere.
  • CloudTrail records who opened a session or sent a command, to which instance, and when, as the docstring says. It does not record the commands typed inside a session, and it hides a Run Command's parameters. Keeping those needs Session Manager session logging and Run Command output sent to S3 or CloudWatch Logs, which this stack does not configure.
def generated_secret(scope: Construct, cid: str, username: str | None = None) -> sm.Secret:
    # No punctuation: the api builds a URL from these, and @ : / % would need encoding.
    return sm.Secret(
        scope,
        cid,
        generate_secret_string=sm.SecretStringGenerator(
            secret_string_template=json.dumps({"username": username} if username else {}),
            generate_string_key="password",
            exclude_punctuation=True,
            password_length=32,
        ),
        # Throwaway account: deleted with the stack. production: RETAIN (a destroyed secret
        # cannot be read back, and the database it opens may outlive the stack).
        removal_policy=RemovalPolicy.DESTROY,
    )


def secret(s: sm.ISecret, field: str) -> ecs.Secret:

    return ecs.Secret.from_secrets_manager(s, field)

A case from the reference build: the test that proved nothing

When the image-push role was first set up, the plan was to prove the trust policy worked by breaking it on purpose. The policy was edited to name the wrong repository, a release tag was pushed, and the job failed with Not authorized to perform sts:AssumeRoleWithWebIdentity, as expected. Then the correct repository name was restored and only the failed jobs were re-run. They failed again.

The policy had been written in the subject format most documentation shows, repo:owner/name:…. This repository's tokens use a form that embeds the numeric owner and repository IDs, which survives renames and stops a deleted-and-recreated repository with the same name from inheriting the trust. Reading the repository's OIDC subject setting showed the real value. With the prefix fixed, all three image copies succeeded, and the digests in ECR matched the ones published to GitHub's registry: the same bytes in a second place.

Two habits come out of this. Check the real claims first, before blaming anything else, because the error never says which condition failed. And re-run failed jobs rather than cutting a new release: it is faster, and it tests exactly the same thing.

How to say it

"Our pipelines don't hold cloud keys. Each job gets a token from GitHub, AWS trades it for one-hour credentials, and the role only trusts a release tag or the production environment."

"Workloads use the role attached to their compute, and people use SSO. If a laptop or a CI log leaks, there is no long-lived credential in it."

Going deeper What a trust policy can and cannot see

GitHub's token carries many claims: the repository and its owner, the ref, the commit, the workflow file, the environment, the event that triggered the run. A trust policy can always test aud and sub, and AWS STS now also accepts several of GitHub's own claims as condition keys, among them repository_id, repository_owner_id, ref, environment and job_workflow_ref. A role can then trust one workflow file directly. AWS advises the immutable IDs over names, because a renamed or deleted repository's name can be claimed by someone else. The subject still matters most, because every cloud's trust policy can match it, and GitHub lets a repository or organization customize which claims are combined into it. Including the workflow file in the subject, for example, is the portable way to let a role trust one specific workflow rather than any job in the repository.

The same customization setting is what produced the immutable form seen in the case above. Reading it, rather than assuming the default, is the reliable way to know what the policy must match.

StringLike allows the wildcards * and ?; StringEquals does not. Use the exact form wherever there is nothing variable to allow, as the deploy role does, so a typo cannot widen the trust.

One OIDC provider entry per issuer is allowed in each account. Several roles can trust the same provider, each with its own conditions, which is how one account serves several repositories and environments.

Questions

  1. What does a CI job need before it can obtain cloud credentials through OIDC, and what does it receive?

    Answer

    The job needs permissions: id-token: write, so the CI platform will sign a token for it, and the cloud account needs an OIDC provider entry that trusts that platform. It presents the token to AWS STS and receives temporary credentials for a role, valid here for at most one hour.

  2. Why does the deploy role trust a GitHub environment rather than a tag or branch?

    Answer

    A job that names an environment gets a subject ending in :environment:NAME. Trusting that subject means GitHub's environment protection rules, such as allowed branches and required reviewers, decide which jobs can reach production. Approvals can then change without editing AWS.

  3. You break a trust policy on purpose and the job fails. What must you check before concluding that the policy works?

    Answer

    That the correct policy actually passes. A failure only proves something if a success was seen first. Otherwise the policy may never have matched, as in the case in this chapter.

  4. What is the difference between an ECS task execution role and a task role?

    Answer

    The execution role is used by ECS before your code runs: to pull the image and to inject secrets. The task role is the identity your code uses to call AWS services while it runs. A task that calls no AWS API at runtime needs no task role.

  5. Why is removing SSH access a security improvement rather than only an inconvenience?

    Answer

    There is no key to leak, no open port to attack, and every session or command is authorized by IAM, and CloudTrail records who opened or sent it, to which instance and when. To keep the commands themselves, turn on Session Manager session logging and Run Command output to S3 or CloudWatch Logs.

  6. Which permission in the image-push role cannot be limited to the three repositories, and how is that handled?

    Answer

    ecr:GetAuthorizationToken, which is account-wide by design. It is granted on * with a comment saying why, while push and pull are granted only on the three repositories.
