Part IV · Getting code onto servers

The deployment ladder, and one VM done properly

Deployment has climbed from copying files by hand to declaring the desired state and letting a platform converge on it, and a single, well-built virtual machine is still a sound first rung if it keeps the habits that make the next rung easy.

At a glance
  • Each rung of the ladder hands one more job to automation: copying, then running, then replacing, then scheduling, then owning the machines.
  • One VM is a good start for a pilot: one host, one script, logs in one place. What matters is that it runs released images, never a checkout.
  • A deploy on one host can drop no requests: start the new version beside the old one, wait until it is healthy, then drain the old one.
  • A proper VM has no SSH key and no open port 22, pulls images with its own role, and is rebuilt from code rather than patched by hand.
  • Keep the rule "CI builds one image per version; deploying means run this version", and moving to a managed platform later is small.

The ladder

Rungs 0 and 1 are where many teams started: log in, copy, restart. Rung 2 is the first that is reproducible, because the server runs an image built by CI. Rung 3 adds capacity and redundancy but leaves N machines to update without taking the fleet down. Rung 4 is the big change in thinking: instead of running commands, you declare what should be running, "two copies of version 0.8.2", and an orchestrator such as Kubernetes or ECS works continuously to make reality match, replacing a few copies at a time. Rung 5 removes the machines from view entirely.

"Serverless" does not mean one very reliable server. It means many small, disposable units that the platform replaces when they are unhealthy. Fargate and Cloud Run run your container images; Lambda runs a zip file or an image in lightweight virtual machines. A Python virtual environment isolates packages but not the operating system's libraries or the interpreter build, which is why a platform that wants an image gains nothing from a virtual environment alone.

One VM, without ceremony

A single VM is the right first home for a pilot with few users, where a short night-time maintenance window is acceptable and the team is new to operations. Where ECS asks a new team to learn roles, task definitions, load balancers and networking at once, a VM is one box, one script and logs in one place. The reference service ran on a VM before it ran on ECS, with the same images.

  • The image goes to a registry, not to Git. The VM pulls it by version, authenticated by its own role on AWS, and never builds anything.
  • The deploy definition matches the version. The compose file and deploy script must match the images, so they come from the same release: shipped by CI with each deploy, or checked out at the release tag. Never a working copy someone edited.
  • The deploy script never stops what works: it pulls the version, runs migrations as a one-off container, starts the new api beside the old one and waits for it to be healthy, drains the old one, and only then records the version, so later commands run it too. If the new api never becomes healthy, the script removes it and stops; the old one was never stopped.
  • Rollback is the same script with the previous version.
In the reposcripts/deploy.shthe rolling deploy for one host

The deploy script opens with its own design: why the obvious command is not used, and the five steps that replace it. It is about 190 lines of Bash, checked by a linter in CI, and its behavior is measured by a failure drill.

  • Migrations run while the old version still serves, which is why they must be backward compatible.
  • The new api is started beside the old one, and nginx must resolve it before the old one stops.
  • Rollback is the same script with the previous version, and the schema is never reversed.
  • Step 5's comment describes nginx owning the port. Further down, the script notes that the edge holds requests while nginx restarts (no request failed), and that it replaces the edge, about 2 s of refused connections, only when the edge's build inputs changed.
#!/usr/bin/env bash
# Deploy a release to this host without refusing requests.
#
#   make deploy tag=1.4.0          images from $IMAGE_PREFIX (ghcr.io/..., see .env)
#   PULL=0 make deploy tag=local   images already on this host (local testing)
#
# `docker compose up -d` replaces a container by stopping it first: the old
# api drains its in-flight requests while nothing accepts new ones (measured:
# 502s for 6.7s, and for as long as the longest answer in flight). Instead:
#   1. migrate (the old api is still serving: migrations must be backward
#      compatible - add first, remove in a later release)
#   2. start the new api NEXT TO the old one and wait until it is healthy
#   3. wait for nginx to resolve it (resolver valid=10s in default.conf)
#   4. stop the old api: it finishes its in-flight requests (streams
#      included, up to graceful_timeout) while nginx sends new ones to the new
#   5. replace nginx: behind the TLS edge no request fails (the edge retries);
#      where nginx publishes the port itself, ~0.3 s of refused connections;
#      then the edge, only if its image changed (~2 s of refused connections)
# Rollback = deploy the previous tag. The database stays as it is (the
# code rolls back, the schema does not), so the previous tag must be able to
# run on it: the expand/contract rule.

The VM done properly

The reference build ran the same stack on an EC2 virtual machine defined in CDK. What makes it acceptable to a platform team, compared with a hand-built server:

  • No SSH key and no port 22. Operators use Session Manager and Run Command, which the instance's role allows. CloudTrail records who opened a session or sent a command; what was typed is kept only with session logging, which this stack does not turn on.
  • No registry password. A credential helper gets ECR credentials from the instance's role.
  • Built from code. cloud-init installs Docker, creates the deploy user, clones the repository for its compose files and scripts, and generates the .env with random passwords at first boot. Because cloud-init runs only once, a changed recipe replaces the VM rather than editing it.
  • Small surface. The metadata service accepts only its token-based version (IMDSv2), the disk is encrypted, and the security group admits HTTP and nothing else.
In the repoinfra/aws/vm.pythe VM's role and its single open port

The VM's identity and its network surface, in fifteen lines of CDK.

  • The role trusts only the EC2 service, and carries one managed policy: the one Session Manager needs.
  • It may pull from the three image repositories, nothing more.
  • The security group's description says it plainly: HTTP in, no SSH.
role = iam.Role(
    self,
    "Role",
    assumed_by=iam.ServicePrincipal("ec2.amazonaws.com"),
    managed_policies=[
        iam.ManagedPolicy.from_aws_managed_policy_name("AmazonSSMManagedInstanceCore")
    ],
)
for repo in repos.values():
    repo.grant_pull(role)

sg = ec2.SecurityGroup(self, "Sg", vpc=vpc, description="HTTP in; no SSH")
sg.add_ingress_rule(ec2.Peer.any_ipv4(), ec2.Port.tcp(80), "the app")

Results on the VM, with requests flowing throughout: the first start of an older release from ECR brought all six services up healthy; the upgrade to the next release migrated, started the new api beside the old one and drained it; and the rollback, across that migration, said "the database is ahead of 0.8.0: rolling back the code only, no migration". 139 requests arrived during the rollback, and none failed.

The reference runbook for a demo VM even includes the request to send IT: Ubuntu Server LTS, 4 vCPU, 8 GB of memory and 40 GB of disk, with the reasoning. The full stack with monitoring idles at about 880 MiB but its memory limits add up to about 5 GiB; images take 2.9 GB, logs are capped per container, and two weeks of daily database dumps fit in about 1 GB.

Agents on hosts, and immutable infrastructure

A monitoring or log-shipping agent is a small background program that works for a remote service; nothing to do with AI agents. It is needed because the container runtime keeps only each container's standard output, and host metrics such as CPU and disk are a separate job. Often the runtime's logging driver is enough on its own, sending container output straight to CloudWatch.

How an agent reaches a host depends on the rung. On plain VMs it is baked into a golden image built by a tool such as Packer, or installed by the first-boot script. On ECS or Cloud Run it is a setting of the service, with no host to touch. On Kubernetes it is a DaemonSet: one copy per node. In every case the host is rebuilt from a versioned definition, never patched by hand. That is what immutable infrastructure means.

When to climb the next rung

Move off the single VM when there are paying customers, when releases must not drop even the brief gap of replacing the only proxy, or when the VM itself becomes a burden to patch and watch. If the habits of this chapter are kept (CI builds one image per version, and a deploy means "run this version"), the move to ECS in Chapter 9 changes where the images run, not how they are built.

How to say it

"For the pilot we run one VM: released images, a rolling deploy that drops no requests, no SSH, rebuilt from code. Moving to ECS later changes where it runs, not how it's built."

Questions

  1. What changes in your thinking between rung 3 and rung 4 of the ladder?

    Answer

    You stop running commands against machines and start declaring the state you want, such as two copies of a version. The orchestrator reconciles reality to that declaration continuously, including replacing failed copies.

  2. Why does recreating a single container cause downtime, and how does a rolling deploy avoid it on one host?

    Answer

    Recreating stops the old container first, so nothing accepts new requests while it drains. A rolling deploy starts the new version beside the old one, waits until it is healthy and reachable, and only then drains the old one.

  3. Why should a VM never run git pull and build?

    Answer

    A checkout can carry edits and drift, and builds on different hosts can differ. Pulling a released image means the host runs exactly what CI tested.

  4. What makes the reference VM acceptable to a platform team?

    Answer

    No SSH key or open port 22, access through Session Manager, with every session recorded in CloudTrail, images pulled with the instance's own role, a single open port, IMDSv2 and an encrypted disk, and a host rebuilt from code at first boot.

  5. When is it time to move from one VM to a managed container platform?

    Answer

    When there are paying customers, when releases must not drop any requests at all, or when the VM becomes a burden. If CI already builds versioned images and deploys mean "run this version", the move is small.
