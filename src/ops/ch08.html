Networking on AWS

An AWS network is built from layers you compose (a private network, subnets that a route table makes public or private, gateways for traffic in and out, and firewalls that name each other), and the safest designs leave only the load balancer reachable from the internet.

At a glance
  • A VPC is your own isolated network in one region. A subnet is a slice of it in one availability zone.
  • A subnet is public or private only because of its route table: public means it has a route to an internet gateway.
  • A NAT gateway lets private subnets reach out without being reachable. It costs money per hour and per gigabyte.
  • Security groups are stateful allow-lists on each resource, and can name other security groups instead of IP addresses: the load balancer may reach the api, and only the api may reach the database.
  • Put the database in a subnet with no route to the internet at all, so a single security group mistake cannot expose it.

A home router, split into AWS resources

A home router does three jobs in one box, and AWS turns each into a separate resource you configure on its own. The mapping is a good way in.

The parts

  • VPC. Your own isolated network, spanning one region, with an address range written in CIDR notation.
  • Subnets. Slices of that range, each pinned to one availability zone. Routing is decided per subnet by its route table, which is the real reason subnets exist. The usual minimum is a public and a private subnet in each of two zones, because load balancers and database subnet groups both require two.
  • Internet gateway. The doorway. A subnet with a route to it is public.
  • NAT gateway. Lets private subnets make outbound connections, to a model provider's API or a package mirror, without accepting inbound ones. It is billed per hour and per gigabyte processed.
  • Security groups. Stateful, per-resource, default-deny allow-lists. Stateful means a reply to an allowed request is allowed automatically. A rule can name another security group as its source.
  • Network ACLs. A coarser, stateless filter per subnet. Most teams leave them at their defaults unless compliance requires more.

The reference network

The reference stack's network is deliberately cheap, and the code says so. It has two zones with public subnets for the load balancer, the VM and the ECS tasks, and isolated subnets for the database, with no route to the internet in either direction. There is no NAT gateway, because nothing in a private subnet needs to reach out. The trade-off is named in the code: tasks get public IP addresses so they can pull images, and they rely on security groups, not subnets, to stay unreachable.

In the repoinfra/aws/network.py

The whole network is about forty lines. Its docstring states the design and its trade-off, and the second excerpt is a fix that only running it could have revealed.

  • Two kinds of subnet: public, and isolated (no route out at all), each a /24 in two zones.
  • nat_gateways=0 saves about six cents an hour plus data charges, at the cost of public addresses on the tasks.
  • The zones are named in code rather than looked up, so the template can be produced without cloud credentials.
  • RDS refused to create the database in the first two zones for lack of capacity. Capacity is per zone and changes over time; a third isolated subnet solved it without touching anything already running.
"""Stages 3-5: one VPC shared by the VM and the ECS stack. A VPC itself costs nothing.

Two availability zones (an ALB and an RDS subnet group both require two). Public subnets hold
the load balancer, the VM and the Fargate tasks; isolated subnets (no route to the internet in
either direction) hold the database. No NAT gateway: nothing in a private subnet needs to reach
out, and one would cost ~$0.06/hour plus data. The trade-off: tasks get public IPs (each
$0.005/hour) and rely on security groups, not subnets, to stay unreachable.
"""
# A constant, not read from the VPC: the app stack trusts proxies in this range
# (FORWARDED_ALLOW_IPS), and a token would make it import from this stack.
VPC_CIDR = "10.20.0.0/16"


class NetworkStack(Stack):
    def __init__(self, scope: Construct, cid: str, **kw) -> None:
        super().__init__(scope, cid, **kw)
        self.vpc = ec2.Vpc(
            self,
            "Vpc",
            ip_addresses=ec2.IpAddresses.cidr(VPC_CIDR),
            # Named, not looked up: synth works without credentials.
            availability_zones=["ap-south-1a", "ap-south-1b"],
            nat_gateways=0,
            subnet_configuration=[
                ec2.SubnetConfiguration(
                    name="public", subnet_type=ec2.SubnetType.PUBLIC, cidr_mask=24
                ),
                ec2.SubnetConfiguration(
                    name="data", subnet_type=ec2.SubnetType.PRIVATE_ISOLATED, cidr_mask=24
                ),
            ],
        )
        # Added after RDS refused 1a and 1b: "no subnets exist in Availability Zones with
        # sufficient capacity ... for db.t4g.micro; choose from ap-south-1c". Capacity is per AZ
        # and changes; an extra isolated subnet (main route table: local routes only) gives the
        # database a third zone without touching the subnets the VM already uses.
        self.data_1c = ec2.Subnet(
            self,
            "Data1c",
            vpc_id=self.vpc.vpc_id,
            availability_zone="ap-south-1c",
            cidr_block="10.20.10.0/24",
        )
        self.db_subnets = [*self.vpc.isolated_subnets, self.data_1c]

Address ranges in CIDR notation

CIDR notation writes a range as an address and the number of fixed bits. 10.20.0.0/16 fixes the first 16 of 32 bits and leaves 16 free: 65,536 addresses. A smaller number after the slash is a bigger range. AWS reserves five addresses in every subnet, so a /24 holds 251 usable ones. A subnet's range caps how many resources it can hold (one address each, not one per connection), which matters for tasks that each get their own network interface.

Toward a production network

The production version of this design moves the tasks into private subnets with no public addresses. Outbound traffic then needs a NAT gateway, and because it is billed per gigabyte, heavy traffic such as image pulls should go through VPC endpoints: private connections to ECR and S3 that skip the NAT gateway. If a security team restricts outbound traffic, the model provider's API host must be on the allowed list, or every assistant request fails. The public DNS record points at the load balancer as an alias, never at an IP address, because the load balancer's addresses change.

How to say it

"Only the load balancer is public. Security groups chain from it to the tasks and from the api to the data, by group rather than by IP, and the database sits in subnets with no route to the internet at all."

Questions

  1. What makes a subnet public?

    Answer

    Its route table has a route to an internet gateway. Nothing about the subnet itself is public or private; routing decides.

  2. Why reference security groups rather than IP ranges in rules?

    Answer

    Tasks and instances come and go with new addresses. A rule that names a group covers every current and future member, so autoscaling needs no rule changes, and the intent ("only the api may reach the database") is explicit.

  3. How many usable addresses does a /24 subnet have on AWS, and why?

    Answer

    251: a /24 has 256 addresses, and AWS reserves five in every subnet.

  4. Why does the reference stack put its tasks in public subnets, and what keeps them safe?

    Answer

    To pull images without paying for a NAT gateway. Their security groups admit traffic only from the load balancer's group, so a public address does not make them reachable. Production would move them to private subnets.
