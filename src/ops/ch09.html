Containers on ECS Fargate

ECS on Fargate runs containers with no servers to manage: you describe each task once, a service keeps the right number running behind a load balancer, and every release is a rolling replacement that rolls itself back if the new version cannot start.

At a glance
  • A task definition is a versioned description of containers: image, CPU and memory, environment, secrets, logs, health check. A service keeps N copies running.
  • A release registers a new task definition revision and updates the service: new tasks start beside the old ones, and the old ones stop once the new are healthy.
  • The deployment circuit breaker rolls a release back by itself when its tasks keep failing to start.
  • ECS has one health signal, the load balancer's check, and acts on it like a liveness check. Point it at a shallow endpoint.
  • Anything that must be counted once across copies, such as rate limits or sessions, needs a shared store. A sidecar in each task counts on its own.

The Compose file stays as the local development environment, and the task definition is its production counterpart. Five Compose containers often become two or three ECS services plus managed services.

Rehearse the task locally first

Most cloud failures are configuration, and a Fargate task can be rehearsed on one machine before any money is spent: containers in a task share one network namespace, which docker run --network container:<first> reproduces, and a plain Postgres container with only an owner user stands in for RDS, which runs no setup scripts. The rehearsal for the reference build found four problems:

  • The production guard worked. With production settings the api refused to start: plain-HTTP cookies and a fake model. Without a domain or a model provider, both were honest exceptions, named one by one in a waiver setting rather than turned off.
  • The web image assumed Compose. Its nginx found the api through Docker's internal DNS, which Fargate does not have. On AWS the load balancer routes /api/* straight to the api and strips the prefix, and nginx only serves files.
  • A rollback trap. Rolling back across a migration made the migration tool fail on a revision it did not know. The migration step was taught to recognize that case and do a code-only rollback (Chapter 13).
  • Least privilege. A setup container creates the application's own database user, allowed to read and write rows but not to change the schema, and does it idempotently, because RDS will not run setup scripts.

How a task starts: init containers

Each api task first runs two short-lived init containers: one creates the least-privileged database user, the next runs migrations as the schema owner. Only when both have exited successfully, and the model sidecar is healthy, does the api container start. Every new task migrates before it serves, which is simple, but tasks can start together (the first deploy starts two), and two migration runs at once collided: one failed. So the runs take turns on a database lock, and a deploy also starts one new task at a time.

One detail of how ECS evaluates those dependencies cost an afternoon. When the database was down, a new task's first init container failed straight away; the second, which depended on it, then never ran; and the api, which depended only on the second, waited forever. The task stayed PENDING for 13 minutes, billed, until stopped by hand.

In the repoinfra/aws/service.pythe api's start conditions

The fix, with the measurement that justified it in the comment. Each dependency names a condition: the init containers must exit with SUCCESS, the sidecar must be HEALTHY.

  • All three are direct dependencies of the api, the essential container: when any fails, the api gives up and ECS stops the task.
  • Each init container also has a 120-second start timeout, the most Fargate allows.
  • The comment keeps the evidence: the chain stuck for more than four minutes; direct dependencies stopped the task in one and a half.
# Every init container is a direct dependency of the essential api: when one fails, the
# api gives up and ECS stops the task. Through a chain (api -> migrate -> dbinit) a dbinit
# that fails fast leaves migrate "stopped" without running, and the task PENDING forever
# (measured with one-off tasks: the chain stuck >4 min; direct: stopped in 1.5 min).
api.add_container_dependencies(
    ecs.ContainerDependency(
        container=dbinit, condition=ecs.ContainerDependencyCondition.SUCCESS
    ),
    ecs.ContainerDependency(
        container=migrate, condition=ecs.ContainerDependencyCondition.SUCCESS
    ),
    ecs.ContainerDependency(
        container=mock_llm, condition=ecs.ContainerDependencyCondition.HEALTHY
    ),
)

A release on ECS

  1. CI copies the release images to ECR, authenticating with an OIDC role (Chapter 5).
  2. The deploy registers a new task definition revision with the new image and updates the service.
  3. ECS starts new tasks beside the old ones, waits for the load balancer's health check, shifts traffic, and stops the old tasks, which finish their in-flight requests first.
  4. If the new tasks keep failing to start, the deployment circuit breaker rolls the service back to the previous revision, and the deploy fails.

Measured on the reference service, with a probe sending requests twice a second: a forward deploy took 3 minutes 17 seconds with 352 requests and none failed, and the deliberate bad release was rolled back in under 8 minutes while the old tasks kept serving. ECS Exec gives a shell into a running task, without SSH, for the rare case that needs one.

One health signal

The reference api follows the Kubernetes convention of two health endpoints. /health answers "is the process alive?" and checks nothing external. /ready answers "should traffic come here?" and requires the database. On Kubernetes they feed two separate probes. ECS has one signal, the load balancer's target health check, and it replaces any task that check calls unhealthy. So a deep check behaves like a liveness check, and a database outage turns into task churn. A drill showed exactly that:

Database stopped for 7 minutesLoad balancer checks /ready (deep)Load balancer checks /health (shallow)

The rule on ECS: point the load balancer at a shallow check; rely on the init containers for readiness at start (migrations succeed only if the database answers); and detect outages with an alarm on 5xx responses. The api reconnected four seconds after the database returned, with no restart.

In the repoinfra/aws/service.pythe service's deployment settings and the api's health check

The service definition and the api target group's health check, each with its reasoning beside it.

  • min_healthy_percent=100 and max_healthy_percent=150: start one new task before stopping an old one, one at a time.
  • The circuit breaker is enabled with rollback.
  • The health check path is /health, and the comment explains why /ready would turn an outage into churn.
  • The deregistration delay covers the longest answer. ECS takes a task out of the load balancer before it sends SIGTERM, and the balancer drops whatever is still in flight when the delay ends: at 30 seconds, long answers were cut during deploys.
return ecs.FargateService(
    self,
    f"{name.title()}Service",
    service_name=name,
    cluster=cluster,
    task_definition=task,
    desired_count=2,
    # A public IP to pull images without a NAT gateway; the SG admits only the ALB.
    # production: private subnets, a NAT gateway or VPC endpoints for ECR and logs.
    assign_public_ip=True,
    vpc_subnets=public,
    security_groups=[sg],
    min_healthy_percent=100,  # start a new task before stopping an old one
    # 150% of 2 = one extra task at a time during a deploy. Tasks still start together
    # (the first deploy, a scale-out): their migrate init containers then take turns on
    # an advisory lock (apps/api/migrations/env.py).
    max_healthy_percent=150,
    circuit_breaker=ecs.DeploymentCircuitBreaker(enable=True, rollback=True),
    health_check_grace_period=Duration.seconds(120),
    # `aws ecs execute-command`: a shell without SSH. production: off, or limited by
    # IAM to the on-call role, with session logging.
# Liveness, not readiness. ECS replaces any task its load balancer calls unhealthy,
# so a deep check (/ready: the database) turns a database outage into task churn:
# measured, every api task marked unhealthy and replacements stuck in dbinit. Kubernetes
# separates the two (readinessProbe /ready, livenessProbe /health); ECS has one signal.
# Readiness at start is covered by the init containers: migrate succeeds only if the
# database answers. A database outage still shows: /api/ready 503 and the 5xx alarm.
health_check=elbv2.HealthCheck(
    path="/health", interval=Duration.seconds(10), healthy_threshold_count=2
),
# ECS takes a task out of the ALB first, waits this long, and only then sends it
# SIGTERM; at the end of the wait the ALB drops whatever is still in flight. So the
# wait must cover the longest chat stream (LLM_STREAM_TIMEOUT_S, 120 s): at 30 s,
# any answer longer than that was cut during a deploy. Deploys wait up to this long
# per task only while requests are in flight.

Scaling out, and the state that must be shared

The api's login endpoint is rate-limited per client: 30 attempts a minute, counted in Valkey. While the api ran with a private Valkey container beside it in each task, scaling to two tasks quietly doubled the limit, because each task counted on its own.

The general rule: a sidecar suits state that belongs to one task. Anything that must be counted once across copies (rate limits, sessions, locks) needs a shared store. The fix shipped through a pull request together with two tasks per service, one per zone, and autoscaling from two to four api tasks on requests per target, capped so that four tasks times one worker times ten pooled connections stays well inside the small database's connection limit (two workers of five at first, until a review matched the task's half CPU to one worker).

Autoscaling takes minutes. Under a steady 80 requests a second, the scaling alarm fired five minutes after the load started and four tasks were running a minute later: about six minutes from load to capacity, made of three one-minute data points, the metric's delay and the task start. The k6 load test that drove it sent 33,601 requests with none failed and a 95th-percentile latency of 58 ms. Autoscaling follows trends, so the minimum count must carry a sudden spike on its own. Stopping one task by hand, as a host failure would, caused no failed requests: ECS started a replacement at once.

Questions

  1. What is the difference between a task definition and a service?

    Answer

    A task definition is a versioned description of the containers to run. A service keeps a number of copies of one revision running, replaces failed ones, and rolls them to a new revision during a deploy.

  2. Why should the load balancer's health check on ECS be shallow?

    Answer

    ECS replaces any task the load balancer calls unhealthy. If the check depends on the database, a database outage makes every task "unhealthy", and ECS churns tasks that cannot help. A shallow check keeps the tasks; the outage is detected by the 5xx alarm instead.

  3. What do min_healthy_percent=100 and max_healthy_percent=150 mean for a service of two tasks?

    Answer

    Never fewer than two healthy tasks, and at most three running: one new task starts, becomes healthy, then one old task stops, and the cycle repeats.

  4. Why did scaling to two tasks double the login rate limit?

    Answer

    Each task had its own Valkey container and counted attempts on its own, so each allowed the full limit. Shared limits need a shared store.

  5. How long does autoscaling take to add capacity, and what does that imply?

    Answer

    About six minutes in the reference build, from the start of the load to the new tasks running. The minimum task count must absorb a sudden spike without help.
