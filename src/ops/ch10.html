Kubernetes and EKS

Kubernetes is a portable orchestrator that keeps declared workloads running through a control loop, with a richer model than ECS (separate readiness and liveness, init containers, an ecosystem of controllers), at the price of a cluster someone must run and a standing cost.

At a glance
  • You declare objects (a Deployment of three replicas of an image); controllers continuously reconcile reality toward them.
  • The control plane (API server, etcd, scheduler, controllers) decides; the nodes run pods. Managed offerings such as EKS, GKE and AKS run the control plane for you.
  • Readiness and liveness are separate probes: one controls traffic, the other restarts containers. ECS has only one signal.
  • Every pod gets a routable IP and services get DNS names, so containers on different hosts find each other the way Compose services do on one host.
  • Pick ECS for a few AWS-only services and a small team; pick Kubernetes for many services, a platform team, portability, or its ecosystem.

The model: declare, then reconcile

Kubernetes inverts the deploy script. Instead of a sequence of commands, you submit objects that describe the end state: a Deployment that says "three replicas of this image", a Service that gives them a stable name, a ConfigMap and Secret for configuration. Controllers then run a loop forever: observe the cluster, compare it with the objects, act on the difference. A node dies, three replicas become two, and the loop starts a third elsewhere without anyone being paged.

Two probes, two questions

The biggest practical difference from ECS for the reference service is health. Kubernetes asks two separate questions. A readiness probe decides whether a pod receives traffic: when it fails, the pod is removed from its Service's endpoints, but keeps running. A liveness probe decides whether the container is stuck: when it fails, the container is restarted. The reference api was written for exactly this split, with /ready and /health.

In the repoapps/api/app/routes/health.py

The two endpoints and the reasoning behind each. They fit Kubernetes probes unchanged.

  • /health checks nothing external, so a database outage never restarts every replica at once.
  • /ready fails only on hard dependencies. The cache and the identity provider are soft: they are reported as degraded but keep the instance ready, so a partial outage does not become a total one.
  • Each check has its own short deadline, so the probe always answers on time.
"""Liveness vs readiness - two different questions, two endpoints.

/health (liveness): "is this process alive and its event loop turning?"
No dependency checks: if the database is down, restarting the api does
not help, and a liveness probe that checks it would restart every replica
at once. `async def` on purpose: it runs on the event loop, so it fails
exactly when the loop is blocked, and never waits for a worker thread.

/ready (readiness): "should traffic be sent here right now?" Checks hard
dependencies. Postgres is one; Redis is not - the rate limiter fails open,
so a Redis outage is reported as "degraded" but keeps the instance ready.
Nor is the identity provider: signed-in users carry on without it. Its
state comes from the background check (app/oidc.py), never a call per
probe. Marking every instance unready over a soft dependency turns a
partial outage into a total one.
"""
@router.get("/health")
async def health() -> dict[str, str]:
    return {"status": "ok"}


@router.get("/ready")
async def ready(request: Request) -> JSONResponse:
    state = request.app.state
    database, redis = await asyncio.gather(
        probe(_ping_database(request), timeout_s=2.0),
        probe(state.redis.ping(), timeout_s=0.25),
    )
    idp = state.oidc.reachable
    body = {
        "status": "ready" if database else "not_ready",
        "checks": {
            "database": "ok" if database else "unavailable",
            "redis": "ok" if redis else "degraded",
            "identity_provider": "unknown" if idp is None else "ok" if idp else "degraded",
        },
    }
    return JSONResponse(body, status_code=200 if database else 503)

Both difficulties the reference build met on ECS are things Kubernetes handles natively: the web image's nginx would have found api:8010 through cluster DNS, and the api's readiness and liveness split would have worked as designed. The same images could run on EKS Auto Mode in about an hour.

Why orchestrators exist at all

Container networking on one host is easy: Compose creates a private network and its service names resolve. Across hosts, that stops. You need IP connectivity between machines and an orchestration layer on top: Kubernetes gives every pod a routable IP through a CNI plugin, and gives services stable names. Placement, health, rescheduling after a node failure, and rolling updates across many hosts are the other jobs a single host never needed.

ChooseWhen
Compose on one hostOne host is enough, and short maintenance windows are acceptable.
ECS, Cloud Run or Container AppsA handful of services, a small team, one cloud. Less to operate and no control-plane bill.
Kubernetes (EKS, GKE, AKS)Many services, a platform team to run it, portability across clouds, or a need for its ecosystem: operators, GitOps, a service mesh. Or the organization already runs it.
How to say it

"For a handful of services ECS is less to run. Kubernetes earns its cost with many services and a platform team, or when the organization has standardized on it, and it would give us separate readiness and liveness for free."

Questions

  1. What is the reconcile loop, and why does it make deploy scripts unnecessary?

    Answer

    Controllers repeatedly observe the cluster, compare it with the declared objects, and act on the difference. You change the declaration, and the controllers make it true, including after failures, so there is no script of steps to run.

  2. What happens to running workloads if the control plane fails?

    Answer

    Running pods keep running, because each node's kubelet carries on. Deploys, autoscaling and recovery from a dead node stop until the control plane is back.

  3. What is the difference between a readiness probe and a liveness probe?

    Answer

    Readiness decides whether a pod receives traffic; failing it removes the pod from rotation without restarting it. Liveness decides whether the container is stuck; failing it restarts the container.

  4. When would you choose EKS over ECS?

    Answer

    When there are many services and a platform team, when portability across clouds matters, when the Kubernetes ecosystem (operators, GitOps, a mesh) is needed, or when the organization already runs Kubernetes.
