Part VI · The reference build

The reference build, end to end

How it all comes together: one change from issue to production, the infrastructure code that runs it on AWS, and what ten measured stages of building and breaking it taught.

At a glance
  • A change travels one path, issue to production, and every gate on it is a file in the repository or a setting that cannot be skipped.
  • Five CDK stacks and two workflows hold the whole deployment. Read them in the order a release travels, and they explain how a version tag becomes a running service.
  • Every stage ended in evidence: a digest compared, requests counted during a deploy, a metric read from the load balancer.
  • Most failures were configuration, and several were invisible until something was measured.
  • A client-side probe reported an outage that never happened: judge availability from server-side metrics.
  • The finished loop: one version tag, and the release is live on ECS 8 minutes 37 seconds later, with no failed requests.
  • A last stage held the code to its own written rules and found eight gaps on the path to AWS; each was fixed and shown before and after. Testing the running system end to end then found four more.
  • The whole reference deployment, VM and ECS stacks included, cost about sixty cents of cloud time, because everything billed by the hour was torn down after each session.

The stages

One change, from issue to production

Every change to the reference service takes the same path, and each step is held by a file in the repository or a setting on GitHub, not by anyone's memory. Chapters 2 to 5 explain the pieces one at a time. Here is the whole path in one place, with the file to read at each step. The timings are from a real release: the fixes in the version this handbook quotes took exactly this path.

Two properties make the path trustworthy. No step depends on someone remembering it: each gate is a file reviewed like code, or a setting only an administrator can override. And every step leaves evidence another person can read later: the issue, the pull request with its checks, the release with its notes, the deploy with its approval.

The infrastructure code, end to end

Everything AWS runs comes from one folder, infra/aws: a single CDK application of five stacks (Chapter 7). Three cost nothing or almost nothing and stay up between sessions: the image registry, the identity that lets CI reach AWS, and the network. Two are billed by the hour and are built for a session and destroyed after it: the single VM of Chapter 6, and the application stack, which holds everything a request touches. Read in the order a release travels, these files are a complete account of how a version tag becomes a running service.

In the repoinfra/aws/README.mdand the registry stack,infra/aws/registry.py

The folder's README draws the path of a request in ten lines, from the load balancer to the containers of one task. The registry stack is the first thing a release touches.

  • The load balancer routes /api, which nginx does in compose. nginx finds the api through Docker's DNS server, which Fargate does not have, so on ECS it only serves files.
  • Image tags are immutable: once pushed, a tag always names the same bytes. The first stage tested it by trying to overwrite one.
  • Lifecycle rules keep storage flat: untagged images expire after 7 days, and each repository keeps at most 20 images.

In the repoinfra/aws/service.pywho may talk to whom, and the database

The application stack starts with its boundaries. Each security group admits traffic from another group, never from an address range, so the rules follow the services wherever their tasks land.

  • Only the load balancer's group is open to the internet, on port 80. The api and web tasks accept traffic from the load balancer alone. The database and the cache accept it from the api alone, and may not open connections of their own.
  • The database lives in subnets with no route to the internet, encrypted, with credentials that Secrets Manager generated (Chapter 5).
  • Each setting a production database would change carries a production: comment: Multi-AZ, deletion protection, longer backups, a final snapshot.

In the repoinfra/aws/service.pythe api container's settings, and its start script,container/api.sh

The api container's environment is where the load balancer and the application meet. Five of these values changed when a review held the code to its own rules (below).

  • ROOT_PATH is /api because the load balancer rewrites /api/ready to /ready before the api sees it, as nginx does in compose.
  • FORWARDED_ALLOW_IPS is the VPC's range. The load balancer appends the client's address to X-Forwarded-For, so only the addresses it added can be believed.
  • One worker per half-CPU task, with a pool of ten connections: four tasks then hold at most forty database connections.
  • The keep-alive outlasts the load balancer's 130-second idle timeout, and the graceful shutdown ends inside the 120-second stop timeout (Figure 12.3).
  • ECS injects each secret as its own variable; api.sh builds the database URL from them before it starts gunicorn.
environment={
    **db_env,
    "APP_ENV": "prod",
    "APP_VERSION": tag,
    "ROOT_PATH": "/api",  # the ALB strips /api, as nginx does in compose
    # Whose X-Forwarded-For to believe: the ALB's addresses, i.e. the VPC. Not "*":
    # an ALB appends the client to what the client sent, so with "*" the left-most
    # entry, which the client wrote, became its address (the sign-in rate limit's key).
    "FORWARDED_ALLOW_IPS": VPC_CIDR,
    # One worker per usable CPU, rounded up (gunicorn.conf.py): a 0.5 vCPU task runs
    # one, and capacity comes from tasks. The pool keeps the connection budget.
    "WEB_CONCURRENCY": "1",
    "DB_POOL_SIZE": "10",  # x 1 worker x 4 tasks: inside a db.t4g.micro's ~80
    # Idle connections: the ALB keeps them 130 s (idle_timeout), so the api must keep
    # them longer, or the ALB reuses one the api has just closed and answers 502.
    "GUNICORN_KEEPALIVE": "140",
    # In-flight requests get 110 s after SIGTERM, inside the 120 s stop timeout.
    "GUNICORN_GRACEFUL_TIMEOUT": "110",
    "REDIS_URL": redis_url,
# The api reads one DATABASE_URL; ECS injects the secret as separate values, so compose
# it here. The generated passwords have no punctuation, so they need no URL-encoding.
export DATABASE_URL="postgresql://${DB_USER}:${DB_PASSWORD}@${DB_HOST}:${DB_PORT}/${DB_NAME}"

In the repoinfra/aws/service.pyrouting at the load balancer

Two listener rules and a default carry the routing the edge does in compose, checked in priority order.

  • Priority 5 answers 404 for the metrics and alert-webhook paths, so the internet never reaches them. Where Prometheus and Alertmanager run, in the compose stacks, they call the api from inside the network.
  • Priority 10 sends /api/* to the api's target group, and a URL rewrite strips the prefix.
  • Everything else falls through to the web service.
  • The rewrite is newer than the CDK construct for listener rules, so it is set on the CloudFormation resource directly: an escape hatch, used when a construct lags the service.
elbv2.ApplicationListenerRule(
    self,
    "Internal",
    listener=listener,
    priority=5,
    conditions=[
        elbv2.ListenerCondition.path_patterns(["/api/metrics", "/api/alerts/alertmanager"])
    ],
    action=elbv2.ListenerAction.fixed_response(
        404, content_type="application/json", message_body='{"error":"not_found"}'
    ),
)
api_rule = elbv2.ApplicationListenerRule(
    self,
    "Api",
    listener=listener,
    priority=10,
    conditions=[elbv2.ListenerCondition.path_patterns(["/api/*"])],
    action=elbv2.ListenerAction.forward([api_tg]),
)
# URL rewrite (ALB, 2025): /api/ready -> /ready. Not in the CDK L2 yet, so set it on the
# CloudFormation resource directly (an "escape hatch").
api_rule.node.default_child.add_property_override(
    "Transforms",
    [
        {
            "Type": "url-rewrite",

In the repoinfra/aws/service.pyscaling and alarms

The service grows with its load and reports when it is unwell.

  • Autoscaling runs two to four api tasks, adding one while each serves over 1,000 requests a minute. The ceiling comes from the database's connection limit, not from the load.
  • Scale-out waits one minute between steps and scale-in five, so the count does not flap.
  • The two alarms watch what users feel: unhealthy targets and 5xx responses. Neither notifies anyone yet; in production they page the on-call through SNS.

In the repo.github/workflows/deploy.ymlthe last mile: a release onto the stack

The deploy workflow (Chapter 5 shows how it gets its credentials) ends in one command: cdk deploy triage-app with the release's version.

  • --exclusively deploys the application stack alone. The other stacks are deployed once, from a workstation, and rarely change.
  • CloudFormation waits until ECS reports the service stable. A release whose tasks keep failing is rolled back by the circuit breaker, and the step fails.
  • The smoke test calls the readiness endpoint through the load balancer, the path a user's request takes.
  • The infrastructure code comes from main and the image from the release, so rolling the application back never rolls the infrastructure back.
# Rolling deploy; CloudFormation waits until ECS is stable. A release whose tasks keep
# failing is rolled back by the ECS deployment circuit breaker, and this step fails.
- name: cdk deploy triage-app
  working-directory: infra/aws

    CDK_DEFAULT_ACCOUNT=$(aws sts get-caller-identity --query Account --output text)

    uv sync --frozen

      -c tag="$TAG" --outputs-file outputs.json

Images: the same bytes in a second place

The release images already existed in GitHub's registry, built for two processor types. They were copied into ECR as whole multi-architecture indexes, and the index digest in ECR matched the original exactly. Then a deliberate test: pushing a different image over an existing version tag. ECR refused, because the repositories have immutable tags, and the digest behind the tag was unchanged. A tag in that registry always names the same bytes.

One surprise: the registry's scan-on-push never ran on the copied images. It fires for ordinary pushes, and the copy took another path. The lesson is general: scanning belongs in the pipeline, before publishing, not only in the registry (Chapter 4).

The first ECS deploy: two failures, both configuration

  • No export named … found. The new application stack referenced the image repositories, which needed new exports from the registry stack, and the deploy had been limited to the new stack alone. Cross-stack references are ordered dependencies: deploy the producer first (Chapter 7).
  • "No subnets exist in Availability Zones with sufficient capacity." The database instance type was listed as available in all three zones, yet two had no capacity at that moment. Capacity is per zone and temporary. An extra isolated subnet in the third zone fixed it without touching anything running (Chapter 8).

After those, the containers started in the designed order (setup, migrations, sidecars, then the api), the readiness endpoint reported the database and cache healthy and the identity provider degraded (there was none in this stage), and internal paths returned 404 at the load balancer as intended.

An outage that never happened

During the bad-release drill, a probe on a developer's machine sent a request twice a second and reported 15 failures. The timeline did not fit: failures began after the bad task was already gone and continued after the rollback. Splitting curl's timings showed why.

The whole loop, with no human step

With the deploy workflow in place, the only human action was pushing a version tag (the environment has since gained a required reviewer, so a release now also waits for one approval). Everything after it ran on its own: the release built, scanned, published and smoke-tested the images and copied them to ECR; the deploy workflow then ran in the gated environment, applied the infrastructure code with the new version, waited for ECS to be stable, and smoke-tested through the load balancer.

Three design choices made this loop safe to leave unattended. The infrastructure code always comes from main while the image comes from the release, so rolling the application back never rolls the infrastructure back. Deploys share a concurrency group without cancellation, so two deploys queue rather than race. And workflow inputs reach shell commands only through environment variables, never interpolated into the script text, which closes a script-injection route.

Those 1,453 expected warnings are how alert fatigue starts. Alert on symptoms users feel (5xx responses, latency, unhealthy targets), not on log warnings. The load balancer is the source of truth for users, and its totals for the session were: 42,434 requests, no load balancer errors, no connection errors to targets, 281 server errors from the api, every one of them during the two deliberate database outages (honest 503s from readiness), and 107 client errors, which were the rate-limit tests' 429s.

Not built, but worth knowing: Container Insights for per-task CPU and memory, tracing through X-Ray or any OpenTelemetry backend (the api already exports OTLP), and CloudWatch Synthetics, which runs probes from inside AWS and would have avoided the false outage above.

A second pass: the running system

Reading finds what the code says; running it finds what it does. The release was then tested end to end, locally and on a fresh stack: sign-in under attack (a replayed callback, a forged state, another provider, a cross-site sign-out, a reused cookie), team isolation, the rate limit with forged addresses, the load balancer's path rules against encoded and dotted paths, and every failure drill. "Every change takes one path, from issue to production, and every gate on it is code or a setting nobody can skip. Questions

  1. Trace a bug fix from issue to production. Which file or setting holds each gate?

    Answer

    The issue form; CONTRIBUTING.md for the branch and commit names; the pre-push hook for lint, types and unit tests; the pull request template and the code owners file; ci.yml, with branch protection requiring all six jobs on an up-to-date branch; the squash-only merge setting; the tag pattern that starts release.yml, and the ruleset that lets only admins create such a tag; release.yml for scanning, building, smoke-testing and copying to ECR; deploy.yml, gated by the aws-demo environment's reviewer, for cdk deploy and the smoke test. A rollback is deploy.yml run by hand with the previous version.

  2. On ECS, why does the load balancer route /api rather than nginx?

    Answer

    In compose, nginx finds the api by name through Docker's embedded DNS server, which Fargate does not have. So on ECS nginx only serves files, and the load balancer does the edge's routing: a rule sends /api/* to the api's target group and rewrites the path, and another answers 404 for the internal paths.

  3. The load balancer keeps idle connections 130 seconds, and the longest answer takes 120. What must the api's keep-alive, the deregistration delay and gunicorn's graceful timeout be, and why?

    Answer

    Keep-alive above 130 seconds (140), so the load balancer never reuses a connection the api has just closed. A deregistration delay of at least 120 seconds (130), because the load balancer drops whatever is in flight when the delay ends, before ECS sends SIGTERM. A graceful timeout below the 120-second stop timeout (110), or ECS kills the process before its requests finish.

  4. A synthetic check from your laptop reports an outage. What do you look at before declaring an incident?

    Answer

    The server-side metrics for the same window, starting with the load balancer's request count and error counts, and the client's own timings: a slow DNS lookup or connect points at the client's network, not the service.

  5. Why does a rollback through the pipeline take about half as long as a release?

    Answer

    It runs only the deploy half. The older images were built, scanned and published when that version was released, so nothing is rebuilt.

  6. Why does the deploy workflow take its infrastructure code from main rather than from the release being deployed?

    Answer

    So that deploying an older application version never rolls the infrastructure back. The application is versioned by its images; the infrastructure moves forward through its own pull requests.
