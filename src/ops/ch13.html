Environments, releases and rollback

Releasing safely means choosing how traffic moves to a new version, deciding in advance how each kind of change is undone, and reaching real users in stages that each end in something you can measure.

At a glance
  • Four ways to move traffic: rolling, canary, blue/green, and feature flags. They protect against different failures.
  • Every kind of change has its own rollback, chosen before shipping: code, schema, configuration, a feature, infrastructure.
  • Rollbacks roll back code, never the schema. Migrations are written expand-then-contract so the previous release runs on the newer schema.
  • A release that contracts what an earlier one expanded cannot be skipped over; release notes name the minimum version they can follow.
  • Reaching users is a staged road (a real host, real sign-in, a real model, a pilot team, then everyone), and each stage has a "done when".

Four ways to move traffic

The reference service uses rolling deploys everywhere, and for subtle regressions it currently relies on "deploy, watch the dashboard for half an hour, roll back if needed", which works because rollbacks are cheap and cross migrations. The next steps, in order of effort, are a canary on one host (a second api service and a weighted upstream in nginx), then the platform's own traffic splitting with automatic analysis against the service's objectives.

Rollbacks roll back code, never the schema

During a rolling deploy, the old and new versions run at the same time against the same database. So a schema change cannot break either of them, and it is done in steps that each leave both versions working. This is the expand and contract pattern.

The rule produced one of the reference service's decision records, after a rollback failed. The procedure had been "deploy the previous tag", and the previous tag's migration tool had never heard of the revision the newer release applied. The deploy stopped before touching anything, so it failed safely, but rollback was impossible across any migration: exactly when a rollback is most likely needed.

ADR-0015accepted

Rollbacks roll back the code, never the schema

Problem
Rolling a release back to one with fewer migrations failed: the older migration tool could not find the database's current revision.
Decision
A deploy never reverses a migration. When the database is ahead of the image, it skips migrating, says so, and rolls out the older code on the newer schema. Reversing a migration is a separate, deliberate step, decided by a person, run with the newer image.
Rejected
Automatic downgrades: the least-tested code in any project, able to lose data, and run under pressure.
See it in
infra/aws/container/migrate.sh on ECS, and scripts/deploy.sh on a VM.
In the repoinfra/aws/container/migrate.shthe decision, carried out on ECS

The migration init container on ECS, in twelve lines. It asks the migration tool for the database's current revision first.

  • If the tool cannot locate that revision, the database is ahead of this release: it prints so and exits successfully, and the older code starts on the newer schema.
  • Any other failure, such as a wrong password or an unreachable host, still fails the task.
  • Otherwise it migrates forward to the newest revision this release knows.

Measured on ECS and on the VM: rollbacks across a migration, under steady traffic, with no failed requests.

# Schema migrations as the owner, before the api starts (an init container).
# On a rollback the database can be ahead of this release: alembic then cannot find the
# current revision, and the right move is a code-only rollback, not a failed deploy.
# Any other error (wrong password, unreachable host) still fails the task.
export MIGRATIONS_DATABASE_URL="postgresql://${DB_OWNER_USER}:${DB_OWNER_PASSWORD}@${DB_HOST}:${DB_PORT}/${DB_NAME}"
if ! out=$(alembic current 2>&1); then
  if printf '%s' "$out" | grep -q "Can't locate revision"; then
    echo "the database is ahead of this release: code-only rollback, no migration"; exit 0
  fi
  printf '%s\n' "$out" >&2; exit 1
fi
exec alembic upgrade head

One rollback per kind of change

Decide, before shipping, how each kind of change will be undone, and practice it once.

Kind of changeRollback
Application codeDeploy the previous version through the same pipeline.
Database schemaDo not. The previous version runs on the new schema; fix forward. A downgrade is a separate, deliberate decision.
ConfigurationRestore the previous value, through the same reviewed path that changed it.
A new featureTurn its flag off.
InfrastructureRevert the pull request and apply; or fix forward. Rolling back the application never rolls back the infrastructure.
A prompt or model (AI features)Switch the version back in configuration (Handbook 1, Chapter 12).

Two more rules keep rollbacks honest. Releases are never skipped when one contracts what another expanded: the reference service's row-level-security release hides every row from a release two versions older, which never says who is asking, so a host must pass through the release in between. And a breaking API change is announced in the release notes, never discovered by a client. The same holds for settings. One release added production checks that stopped an older host's api until its settings changed, and its notes, a list of pull request titles, did not say so. The reference release notes now open with the settings added to or removed from .env.example since the previous release.

Handing a service to an infrastructure team

A service that can be released safely also has to be operable by someone else. These are the questions an infrastructure team asks, with the reference service's answers. Every answer points to something already in the repository.

They askThe reference service's answer
What runs?Three images (api, web, an HTTPS edge), one migration command, Postgres with pgvector, Valkey, a model provider, an OIDC identity provider.
Health?A liveness endpoint that checks nothing external, a readiness endpoint that checks the database with a real query, and a proxy health check.
Resources?For the api, 2 CPUs and 1 GiB carry about 1,000 signed-in reads a second or 500 concurrent streams; it idles at about 170 MiB. Every container has CPU and memory limits and no swap.
Configuration?A documented settings table, secrets marked; production refuses unsafe values at startup.
Logs, metrics, traces?JSON lines on standard output with a request id; Prometheus metrics; optional OpenTelemetry traces with ids and counts, never content.
Deploy order and stopping?Migrations, then the api (rolling, readiness-gated), then web. On SIGTERM, up to 120 seconds of drain for streams.
Outbound traffic?The model provider and the identity provider over HTTPS; certificates; optionally a trace collector. Nothing else.
Scale and its limits?The api is stateless and scales out; the connection budget allows about 12 replicas before the pooler needs raising; the model provider's quota binds first in real use.
Backups?Postgres only, copied off the host; the cache is disposable. A backup counts once it has been restored.

The road to real users

How to say it

"Every kind of change has a rehearsed rollback: code by redeploying the previous version, features by flag, and the schema never, because migrations are expand-then-contract."

"We roll out in stages, and each stage ends in a measurement: a timed restore, real sign-ins per role, the eval gate on the production model, a pilot that held its objectives."

Questions

  1. What does a canary catch that a rolling deploy does not?

    Answer

    Regressions that do not crash anything but show in the numbers: higher error rates, slower answers, worse quality. A rolling deploy only waits for health checks, then moves all traffic within seconds.

  2. Why is a column rename done across several releases?

    Answer

    Because during a rolling deploy the old code still runs against the database. Adding the new column, writing both, backfilling, switching reads, and only later dropping the old column keeps every running version working at every step.

  3. What should a deploy do when the database is ahead of the image it is deploying?

    Answer

    Treat it as a rollback: skip migrations, say so, and run the older code on the newer schema. Reversing a migration is a separate decision made by a person.

  4. Why does each stage on the road to real users need a "done when"?

    Answer

    Each stage introduces one new kind of risk. A measurable exit (a timed restore, real sign-ins per role, the eval gate on the production model) proves that risk is handled before the next one is added.
