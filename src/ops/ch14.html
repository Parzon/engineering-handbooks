Part VII · Operating it

Cost, teardown and lessons learned

Cloud cost is a design property you can see per hour and per component, teardown is a procedure worth writing down and testing, and the small operational mistakes of a real build are the lessons most worth passing on.

At a glance
  • Split stacks by what bills by the hour, so the expensive parts can be destroyed and recreated in minutes.
  • Know the hourly price of every component before it runs; the reference ECS stack cost about $0.17 an hour.
  • Teardown has an order: first stop anything that would recreate the stack, then destroy, then check for leftovers.
  • A failed teardown is fixed in the code too, so the next one works.
  • Most lost time in a real build comes from small habits: reading the failing step, chaining commands safely, never killing by pattern, never sharing a checkout.

What it cost, per hour

The reference ECS stack's cost is written into its own code, component by component. Roughly half is compute, and the rest is spread over the managed services that replaced containers.

Two numbers put this in perspective. The whole reference deployment, a VM for about 45 minutes and the ECS stack for about three hours, came to roughly sixty cents. And the permanent parts (image repositories holding about 1.3 GB, the CI roles, the network) cost cents a month, so they stay, and the pipeline keeps copying each release into the registry.

Teardown, in order

In the repoinfra/aws/ops.shthe leftovers check

A small operator script holds the commands people need under time pressure. Its leftovers command lists everything that could still be billing after a teardown, one resource type per line, so an empty list means an empty bill.

  • It checks stopped instances too: a stopped VM still pays for its disk.
  • It lists stacks in every non-deleted state, so a half-failed delete shows up.
leftovers)
  echo "EC2:";  aws ec2 describe-instances --filters Name=instance-state-name,Values=pending,running,stopping,stopped --query 'Reservations[].Instances[].[InstanceId,InstanceType,State.Name]' --output text
  echo "RDS:";  aws rds describe-db-instances --query 'DBInstances[].[DBInstanceIdentifier,DBInstanceStatus]' --output text
  echo "ECS:";  aws ecs list-clusters --query clusterArns --output text
  echo "ALB:";  aws elbv2 describe-load-balancers --query 'LoadBalancers[].LoadBalancerName' --output text
  echo "NAT:";  aws ec2 describe-nat-gateways --filter Name=state,Values=available,pending --query 'NatGateways[].NatGatewayId' --output text
  echo "EIP:";  aws ec2 describe-addresses --query 'Addresses[].PublicIp' --output text
  echo "EBS:";  aws ec2 describe-volumes --query 'Volumes[].[VolumeId,Size,State]' --output text
  echo "Stacks:"; aws cloudformation list-stacks --stack-status-filter CREATE_COMPLETE UPDATE_COMPLETE UPDATE_ROLLBACK_COMPLETE ROLLBACK_COMPLETE --query 'StackSummaries[].StackName' --output text ;;

The teardown failed once. CloudFormation deleted the database and its password secret within two seconds of each other, because the template referred to the secret only inside a dynamic reference, which does not order deletes. The database was already gone, but its delete handler could not read the password, so the stack ended in DELETE_FAILED. It was finished by deleting the stack again while retaining the resources that no longer existed, and fixed in code with an explicit dependency (Chapter 7). A full check afterwards found nothing left: no instances, databases, clusters, load balancers, addresses, volumes, caches, alarms, secrets or snapshots.

Lessons from a real build

None of these is dramatic. Together they cost more time than any of the cloud's own surprises.

SymptomCauseFix
A security check failed on a pull request that changed nothing relatedA new advisory against the base image; main already had the fixRead the failing step before touching anything; update the branch.
A rate-limit test failed once on main and passed on its pull requestThe test depends on where a one-minute window fallsRecord it as a flake and make the timing controllable; never retry it silently.
pkill -f pattern killed the operator's own shellThe pattern also matched the command line running the killKill by process ID, never by a pattern the killer itself contains.
Code that had just failed lint was committedCommands chained with ;Chain with &&.
A branch and its files vanished mid-task; commits appeared that nobody on the task madeAnother person or automated coding agent was working in the same checkout and switching branchesOne worktree per parallel session; check the current branch before each commit; stage explicit paths; read git log on main before pushing.
Build output containing account details was swept into a commitA broad git add swept in build outputIgnore generated directories from the first commit; history keeps what was pushed.
An infrastructure pull request could not be merged by its only authorRequired reviews, and no second reviewer yetAn administrator override, used deliberately and flagged in the pull request.

The shared-checkout incident deserves one more sentence, because coding agents make it common. The safe response was the same as for any surprise: stop, read git status, git log and the open pull requests before changing anything; follow the decision already merged rather than fighting it; recover files from Git's own history; and rebuild the change on a fresh branch from the current main.

How to say it

"We know the hourly cost of every component, and everything billed by the hour lives in one stack we can destroy and recreate in about fifteen minutes. Teardown is scripted, including the leftovers check."

Questions

  1. Why is the first teardown step disabling the deploy workflow, not destroying the stack?

    Answer

    With the deploy workflow wired up, the next release tag would start a deploy that recreates the whole stack once someone approves it. Deleting the secret that lets the deploy run makes the teardown stick.

  2. Which item of the reference stack's hourly cost surprises people most, and what does it suggest?

    Answer

    Public IPv4 addresses, the second-largest item. Production networks keep tasks on private addresses behind a load balancer, which also removes them from the internet.

  3. What should happen after a teardown fails halfway?

    Answer

    Finish it (for example by retaining resources that are already gone), check for leftovers, and fix the cause in code so the next teardown works.
